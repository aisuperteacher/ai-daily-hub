🟡 建议看｜Claude Code 2.1.288：MCP OAuth、Code Review 与 Mods 的实用增强

GitHub Release 时间为 2026-10-02 20:19 UTC，即北京时间 10 月 3 日 04:19。

1）内容是什么

2.1.288 主要新增：

  • Mods 新增 $.ui.selection()，可读取 Fullscreen 中最近一次选中文本以及对应 Transcript Row；
  • Cloud Session 即使镜像里没有 GitHub CLI，也有内置 gh api；
  • Ctrl+C 清掉的 Prompt，可以按 ↑ 恢复，包括粘贴文本和图片；
  • MCP Server 在 Tool Call 中途要求新增 OAuth Scope 时，会触发重新认证提示；
  • /code-review 新增 --max-findings <n>|all，可控制 Review 最多输出多少条 Finding；
  • Agents View 增强 Session 搜索和导航。

TypeScript Agent SDK 同步发布 0.3.288，本身无额外独立功能，主要与 Claude Code 2.1.288 parity。

2）核心变化 / 关键知识点

对生产 Agent 最有意义的是 MCP OAuth Scope 升级。真实 OAuth 不是“登录一次后永久可用”，更合理的状态机是：

CONNECTED
AUTH_REQUIRED
SCOPE_UPGRADE_REQUIRED
READY

例如 Tool A 只需 read scope，Tool B 需要 write scope；当前 token 权限不够时，Runtime 应返回可恢复的重新授权状态，而不是普通 500。

/code-review --max-findings 也体现一个重要工程原则：Code Review 不应只追求 Finding 数量，而要控制 Finding 数量 × 准确率 × 严重度 × 人工 Review 成本。

3）为什么有价值

价值主要集中在 MCP OAuth Lifecycle + Review Output Budget + Mod/UI Integration。不是架构级 Breaking Change，但属于 Coding Agent 日常生产化必须补齐的细节。

4）适合场景

Claude Code、MCP、OAuth MCP Server、PR Review、Mods、Cloud Session、多人代码审查。

5）对 Java / AI 工程的具体帮助

Java MCP Gateway 可以保存：

connectionId
grantedScopes
requiredScopes
tokenExpiresAt
authState

Tool 执行前比较 requiredScopes ⊆ grantedScopes，不满足则进入可恢复认证流程。Code Review 可以把 maxFindings、minSeverity、confidenceThreshold 变成 Repo Policy。

6）现在是否值得安装 / 试用

现在不要安装 2.1.288。 正确做法是了解它引入的能力，但当前安装直接使用 2.1.291，因为后续版本修复了 2.1.288 引入的退出时尾部消息丢失回归。

7）优先级

🟡 建议看；作为当前安装版本则可跳过。

🔴 必看｜Claude Code 2.1.289：Managed Permission 不能被 Mod 覆盖，Symlink 不能绕过 Read Deny。

🔴 必看｜Claude Code 2.1.289：权限判断必须作用于“真实资源和真实副作用”

官方 Release 时间 2026-10-03 23:07 UTC，即北京时间 10 月 4 日 07:07。

1）内容是什么

2.1.289 最重要的安全修复有两条：

  1. Managed Machine 上，Compound Shell Command 内部某个嵌套命令命中组织 deny 或 ask 规则时，不能因为用户安装的 Mod 批准了它，就把组织 Policy 覆盖掉。
  2. Read deny 规则现在同样作用于 @ mention 文件、IDE changed file、IDE selected file、通过 symlink 指向的文件，避免 Agent 通过不同资源引用方式绕过读取限制。

该版本还修复 2.1.288 的 claude auth status 变化可能导致更频繁登出的 VS Code 回归，并处理 Plugin/Mod 渲染和验证问题。TypeScript Agent SDK 同步到 0.3.289，主要与 2.1.289 parity。

2）核心变化 / 关键知识点

Policy 优先级必须单调收紧

Organization / Admin Policy
           ↓
Machine Policy
           ↓
Project Policy
           ↓
Plugin / Mod
           ↓
Session

下层可以继续收紧，但不能把上层 DENY 重新变成 ALLOW。

Path Authorization 不能依赖字符串

错误做法：

if (path.startsWith(workspace)) {
    allow();
}

正确思路：

input reference
  ↓
normalize
  ↓
resolve symlink
  ↓
canonical resource
  ↓
policy evaluation

3）为什么有价值

共同原则是：安全策略应该约束实际发生的动作，而不是 Tool 参数或输入字符串表面长什么样。

4）适合场景

企业 Claude Code、Managed Settings、Mods、Plugins、Shell Tool、IDE、文件读写 Agent、Windows/Linux、受监管开发环境。

5）对 Java / AI 工程的具体帮助

Java Tool Gateway 可采用：

RawToolCall
  ↓
Canonicalize
  ↓
ResolveResource
  ↓
OrganizationPolicy
  ↓
ProjectPolicy
  ↓
SessionPolicy
  ↓
Execute

文件审计建议保留 requestedPath、canonicalPath、symlinkResolved、policySource、decision。

6）是否值得立即阅读 / 试用

值得。以今天视角最终仍应直接使用 2.1.291，但 2.1.289 的安全修复必须纳入理解和回归测试。

🔴 必看｜Anthropic Models API：直接查询模型是否支持 thinking.disabled

1）内容是什么

Anthropic 10 月 5 日更新 Claude Platform：GET /v1/models 与 GET /v1/models/{model_id} 新增：

capabilities.thinking.types.disabled

用于告诉调用方某模型是否接受：

{
  "thinking": {
    "type": "disabled"
  }
}

2）核心变化 / 关键知识点

这是从：

Model Name Based Routing
        ↓
Capability Based Routing

的关键一步。不要再写：

if (model.startsWith("claude-sonnet-5-5")) { ... }

而应该通过 Models API 建立 Capability Profile，再动态构造请求。

3）为什么有价值

Sonnet 5.5 已证明模型升级会改变 Thinking、Tool Choice、Computer Use、Advisor 等协议行为。Capability 字段比不断增加 if model == ... 更可靠。

4）适合场景

Java AI Gateway、多模型 Router、Claude API、Fallback、Provider Adapter、Model Registry、长期 Agent。

5）对 Java / AI 工程的具体帮助

建议维护：

ModelCapabilityProfile {
    modelId
    line
    supportsThinkingDisabled
    supportedThinkingTypes
    provider
    lifecycleStatus
}

Fallback 时重新 resolve capabilities → normalize request → invoke，而不是只换 Model ID。

6）是否值得立即行动

值得，尤其是统一 Claude 模型和多 Provider 的 Java Gateway。

🟡 建议看｜OpenAI Java 4.76.0：Agent Session Webhook 让 Agent Runtime 事件驱动

GitHub Release 页面日期 10 月 4 日 18:40 UTC，北京时间 10 月 5 日 02:40。

Agents Session Webhook 当前支持：

OpenAI Agent
   ↓

→ fast ACK
→ queue
→ async processing

🔴 必看｜OpenAI Decisions API：把有限选项判断从开放式生成中拆出来

1）内容是什么

OpenAI 10 月 6 日发布：

POST /v1/decisions
model = gpt-6-luna

官方定位：将文本和图片转换成 typed answers，速度可达到 Responses API 的约 10×。

API 支持：

predicate
choice
score

并按问题顺序返回 probability、choice/confidence、score probabilities/confidence，或 per-question refusal。

Java 官方 Reference 已提供：

DecisionCreateParams params = DecisionCreateParams.builder()
    .input("...")
    .model("gpt-6-luna")
    .addPredicateQuestion("...")
    .build();

Decision decision = client.decisions().create(params);

2）核心变化 / 关键知识点

这不是另一个更快的 Chat Completion。它最适合：

应该走哪个 Workflow？
是否满足条件？
属于哪个类别？
风险等级是多少？
哪个候选更适合？

当前限制：

  • String 或仅含 user role 的 Message；
  • Text + inline image；
  • Image 必须 Data URL，不支持外部 URL/File ID；
  • 一次最多 128 个 Image Part；
  • 不支持 Function Call、File、Audio、Item Reference。

3）为什么有价值

很多 Agent 把低熵选择也交给大型 Reasoning Loop：

Input
→ Responses
→ 长推理
→ 最后只需要 A/B/C

Decisions 可以变成：

Input
→ Decision
→ Typed Result

减少 Latency、Token、Prompt Complexity 和 Parsing Complexity。

4）适合场景

Agent Router、Ticket 分类、风险判断、Approval Routing、客服意图、文档/图片审核、Voice Agent Action Selection、多模型 Router。

5）对 Java / AI 工程的具体帮助

统一 AI Gateway 可以分：

Open-ended task
→ Responses / Agent

Finite decision
→ Decisions API

但 AI Decision 不能直接等于 Business Authorization。推荐：

AI Decision
   ↓
confidence threshold
   ↓
deterministic policy
   ↓
business authorization
   ↓
side effect

6）教程类：建议直接做的小练习

拿一个 Spring Boot Router：

输入：用户问题

Decision questions：
1. 是否属于订单问题？
2. 是否需要人工审批？
3. 风险等级 1~5？

对比：

Decisions API
vs
Responses + Structured Output

记录 Accuracy、p50/p95、Cost/task、Refusal Rate、Confidence Calibration，验证官方“10× faster”在你真实环境中的结果。

7）优先级 / 迁移成本

🔴 必看。 新增 API，不破坏现有 Responses，迁移成本低，值得加入 AI Gateway Capability Matrix。

🔴 必看（Windows / Remote MCP）｜Codex 0.160.1 Hotfix

1）内容是什么

OpenAI Codex Stable 0.160.1 修复：当 Unix Host 使用显式 Remote Env 启动 Windows Executor 的 Remote stdio MCP 时，保留 SYSTEMROOT、TEMP、TMP，避免把 Windows Executor 启动所需基础环境覆盖掉。

2）核心变化 / 关键知识点

错误做法：

remoteEnv = userConfiguredEnv

正确模型：

executorBaseEnv
   +
approvedRemoteOverrides

并保护 OS Critical Variables。

3）为什么有价值

跨 OS Agent 经常会把环境变量问题表现成 MCP 启动失败、临时目录错误或进程异常，非常难查。

4）适合场景

Windows、Remote MCP、Remote Executor、跨 OS Agent、企业开发环境。

5）对 Java / AI 工程的具体帮助

Process Manager 不要 environment.clear() 后全量覆盖，而应采用 Base Env + Approved Overrides + Protected OS Keys。

6）是否值得立即升级

Windows / Remote MCP 用户直接 0.160.0 → 0.160.1。其他用户升级成本也极低。

7）优先级

🔴 Windows/Remote MCP 必看；其他用户 🟡 建议看。
