二、重点更新逐条七维分析

1. Anthropic — Self-hosted Claude Managed Agents（必看）

① 官方标题、内容、日期、级别及直接来源。 Anthropic Claude Platform 官方更新日志于 2026-11-12 宣布 self-hosted Claude Managed Agents。官方总览、快速入门、托管版差异、Kubernetes 部署、数据与访问均可直接阅读。官方称“已推出”，但安装包须联系 Anthropic 客户团队申请；未公开统一的独立产品版本号、镜像 digest、可自助购买地区或本次功能的新 Token 价格，所以不编造。

② 核心技术变化和工作机制。 与“只把工具执行放进自己的沙箱”不同，此模式把 Agent API/loop、Agent/Session 历史存储、Worker 分派、执行沙箱都部署在企业基础设施上。官方组成如下：cma-server 处理 Agent API 与编排；PostgreSQL 16+ 保存状态；ant beta:worker 或 SDK Worker 轮询任务并在隔离容器/VM 中执行 Shell 与文件工具；模型调用仍发给企业选定的推理提供方。官方同时给出了三种独立凭据：Server API Key（应用到 CMA 服务）、Inference Credential（CMA 服务到模型）、Environment Key（Worker 到队列）。

官方说明自托管 CMA 与托管服务整体使用同一 Managed Agents API，并非完整 Claude Messages API 服务器：/v1/messages、/v1/models 在 CMA Server 上会返回 404。自托管版缺少托管 Cloud Environments、Files API、内置文档 Skills、Scheduled Deployments、Dreams、Webhooks；对 Skill ZIP、Multiagent 类型、MCP/Git 主机白名单等也存在差异，迁移前必须逐项读取差异表。不是“只换 Base URL 就百分百兼容”。

③ 为什么有价值，及证据边界。 对数据驻留、租户隔离、企业自有模型路由、任务持久化、审计和私有网络出站控制，这是一个实质性的产品形态改变。以前自托管沙箱时，管理服务与对话历史仍由 Anthropic 托管；现在可由企业自己控制。但自托管不等于推理离线：每次请求仍向推理服务商发送会话上下文，包括 Prompt、Tool 输入与输出。官方未提供经独立复现的吞吐、P95、运维成本或比托管版更便宜的结论，不能据此宣传“性能提升 X 倍”或“数据绝不出网”。

④ 适用产品和业务场景。 适合企业内部 Coding Agent、受监管文档处理、金融分析 Agent、访问私有代码仓库的服务、需要 IAM/SSO 与可审计工具执行的业务流程，以及自建跨云 Agent 平台。不适合只是想简单调用模型的轻量应用：它增加数据库、容器编排、运维、备份、网络策略、凭据轮换和版本升级责任。若只需要工具在内网运行，先考虑 Self-hosted Sandboxes，而不一定部署整套 CMA。

⑤ 对 Java/Spring Boot、Nacos、领域 Gateway、跨语言架构和业务治理的帮助。 可以将 cma-server 视为有状态 Agent 控制平面，模型 Gateway 视为推理数据平面，Worker/沙箱视为不可信工具执行平面。Spring Boot 的企业服务可通过官方兼容 API 或企业适配层调用它；Nacos 可保管服务发现和非敏感配置，不负责持久化会话与日志。数据库和事件链须记录 tenant_id / agent_id / session_id / tool_call_id / idempotency_key / provider / model_id / trace_id。Gateway 对 ANTHROPIC_BASE_URL 路由应区分“应用调用 CMA Server”与“CMA Server 调用模型提供方”，避免误把地址设为自身造成回环。MCP/Git 主机采用准入白名单，Worker 只获得必要资源；不能把模型的安全提示词当成容器隔离。官方要求依信任边界隔离部署；Agent 的 Bash 实际具有 Worker 容器/VM 所赋予的 OS 与网络权限。

⑥ 可实践部署、命令、配置、迁移和生产验收。 前提是企业已经通过官方渠道取得对应发行包。官方给出单机 Docker Compose 开发测试流程；正式部署建议使用发行包内两套 Helm Chart，并准备 Kubernetes 1.30+、PostgreSQL 16+、隔离 Sandbox、可执行 NetworkPolicy 的集群。以下示例只供隔离 Linux 测试环境操作（不是用户 Windows 本机可直接复制运行的完整生产脚本）：

# 在取得并核验官方发行包后，进入包中实际存在的 compose 目录
cd /path/to/extracted-release/compose
# 事先按官方 quickstart 建立 .env，放入演示专用密钥，权限 chmod 600
# 禁止把 .env、数据库口令或 Token 上传到公开仓库
docker compose up --build -d
docker compose logs -f cma-server
curl -s http://127.0.0.1:8400/cma-server/readyz
# 完成测试后停止；默认保留数据库卷
docker compose down --remove-orphans

官方标准快速入门要求 Docker Compose Plugin、openssl、ant CLI 和至少 2 CPU。开发栈使用明文 HTTP，仅绑定 127.0.0.1:8400；官方警告旧版 Docker Engine 在某些条件下仍可能被局域网访问。绝不可直接暴露公网。 获得服务器后，客户端可在专用的 PowerShell 7 测试会话中设置临时环境变量（只填自己的测试凭据，不打印真实密钥）：

$env:ANTHROPIC_BASE_URL = 'http://127.0.0.1:8400'
$env:ANTHROPIC_API_KEY = '<TEST_CMA_SERVER_API_KEY>'
ant beta:agents list
# 测试完成关闭这个 PowerShell 会话；切勿在同一会话启动模型后端/Compose

关键验收：A. readyz 为 ready，PostgreSQL 重启后 Agent/Session 历史仍在；B. Agent 执行 hostname 显示专属 Sandbox 容器名，而非宿主机；C. Worker 断连后任务状态可观测，恢复不重复执行不可逆操作；D. 无权限 Git/MCP/网络出站被拒绝；E. Server、推理与 Environment 三类凭据彼此隔离并可轮换；F. 用例验证 404/400、不支持的 Skills/Webhook/文件资源，迁移不丢关键功能；G. 通过 OTel 与 Gateway 统计请求、Token Usage、成本、P95、失败与恢复；H. 生产 IAM、加密、备份、网络策略、升级/回滚与数据删除覆盖 DB 及备份。

模型和兼容性专项： 这次发布不是新的 Claude 模型或 SDK Model ID；示例 Agent 使用 claude-opus-5-5，不等于所有账户的默认模型。具体 Context、Adaptive Thinking、tool_choice、消息 Schema、MCP、函数工具、Java SDK 版本、许可、隐私和 Token 价格，必须按所选推理提供方及资格单独核实。自托管 CMA 的应用客户端设置 ANTHROPIC_BASE_URL 指向 CMA Server；服务器推理侧应配置真实模型服务或企业 Gateway，不能误用相同 URL。官方还指出使用 Claude API 推理时，模型请求会携带会话/Agent/环境标识头，需纳入隐私审查；模型厂商的数据留存政策不会因为 CMA 自托管而自动失效。

⑦ 是否立即行动与优先级。 必看、值得做架构评估与隔离试验；不建议未获许可就部署或直接替换生产 Agent Runtime。 只有业务明确需要会话数据自主控制、独立推理路由与长期运维时，完整自托管才可能优于托管型；否则选更轻的托管 Agent/自托管 Sandbox。

2. OpenAI — Codex CLI 0.167.2 的 Vertex AI 增量工具更新（建议看；历史遗漏补录）

① 官方信息和日期。 官方标题 Release 0.167.2，正式稳定版，GitHub 原始发布于 2026-11-11 22:44 UTC（北京时间 11 月 12 日 06:44）。昨天日报基线仍记录 0.167.1，因此今天作为遗漏补录，不是冒充 11 月 13 日新发。官方 Release。另外 0.170.0-alpha.4 于 11 月 12 日 22:59 UTC（北京时间 11 月 13 日 06:59）出现，但明确为 Pre-release，只列状态观察，不与稳定版混同。

② 技术机制。 发布说明明确：Codex 在 Google Cloud Vertex AI 渠道默认增量发送工具更新（incremental tool updates）。官方给出的退出开关是 config.toml [features] 下 incremental_tools_legacy_gcp = false。它影响的是工具相关信息在该渠道上的发送行为，而不是公开宣称增加新模型、改变 Java SDK 或提升基础模型智力。

③ 价值及证据边界。 对使用 Vertex AI 承载的 Codex 工作流，增量更新有机会改善工具进度事件的及时性与交互式可观测性，但官方本条未提供定量 P95/Token 节省指标；不同 Gateway 是否完整转发增量事件，需要本地回归，不应直接宣传降低成本。

④ 业务场景。 Google Cloud Vertex AI 上的 Codex 运行、云侧编码 Agent、MCP 工具操作、CI 自动修复、需要采集工具执行事件的运维平台。如果使用原生 OpenAI API 或其他 Base URL，此改动未被官方证明会产生同样影响。

⑤ 企业架构具体帮助。 Gateway 应区分 tool_call_started / delta / completed / failed，按 tool_call_id 聚合增量事件，并做好无序、重复、丢包、断线后的恢复。推理端的增量工具事件与 Agent 工作流完成不是同一层概念：收到最后一个 delta 不等于后续数据库写入已经成功。Java/Spring Boot 可在 SSE 订阅端维护有限状态机；请求/响应 Schema、第三方协议及埋点应随路由区分。

⑥ 测试命令和验收。 在 Windows PowerShell 测试环境记录当前安装与版本来源，不要直接把 Alpha 覆盖稳定版：

codex --version
npm view @openai/codex version
# 如使用官方 npm 渠道，在测试机固定版本：
npm install -g @openai/codex@0.167.2
codex --version

仅对确实使用 Google Cloud Vertex AI 的测试配置，比较默认增量模式与官方声明的退出开关；执行只读工具、长工具、失败工具、断流重连四类样本，验收 tool_call_id 不错乱、日志不重复计费、恢复不重放不可逆指令，并保存能回滚的原配置。0.170.0-alpha.4 仅适合隔离评估，不据其名称推测已经具备新功能。

⑦ 优先级。 建议看。 Vertex AI / Codex 集成团队可安排回归后升级；不用 Vertex AI 的用户可以只关注，不必为了这条改动立即迁移。

七、综合判断

今天最有价值的变化是企业级 Agent 运行时的部署边界改变，不是又出现一个大模型榜单。 Anthropic 允许把 Managed Agents 控制平面及数据存储放入企业自己的基础设施，这对私有数据、审计、云服务商选型和跨语言 Gateway 的设计有重大意义，同时也带来沙箱安全、数据库、网络、升级与运行成本责任。它适合有明确数据驻留与合规需求的团队，不等于所有企业都应自托管。

Codex 0.167.2 则是范围较窄、但值得 Vertex AI 集成团队排查的工程兼容性补录。其余厂商在本次可核验官方证据内没有足以认定的同窗口重大发布；对动态资料缺口如实保留待核验，不杜撰版本、价格、Benchmark 和可用性。
