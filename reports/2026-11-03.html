全球 AI 大模型与 Agent 技术官方日报

核验窗口：以 2026 年 11 月 2 日的日报为基线，检查至 11 月 3 日早间。美国当地 11 月 2 日发布、北京时间今天早间可见的正式更新纳入本期。本期重点关注 Google Gemini 模型退役和自动路由、Anthropic 长会话 Message Threads Beta，以及 Qwen Code 正式版升级。全部按实际业务风险排序，不按厂商平均分配条目。

一、Google｜Gemini 2.5 Pro / Flash 退役及自动模型迁移

官方标题：Gemini API Release Notes — November 2, 2026

原始发布日期：2026-11-02｜计划切换：2026-12-01｜状态：Deprecated｜优先级：必看

官方来源：Gemini API 更新日志 · 模型退役记录 · Gemini API 定价。

1）更新内容、准确 Model ID 与发布范围

Google 于 11 月 2 日正式宣布两项模型退役安排：

旧 Model ID 12 月 1 日计划自动路由至 计费口径
gemini-2.5-pro gemini-3.8-flash 按 Gemini 3.8 Flash 费率
gemini-2.5-flash gemini-3.5-flash-lite 按 Gemini 3.5 Flash-Lite 费率

这两个旧模型目前已经从 Google AI Studio 可选模型中移除。12 月 1 日后旧 ID 请求将自动指向替代模型。 风险不一定表现为失败，也可能表现为请求成功但能力与费用改变。此公告直接针对 Gemini API；Vertex AI 的 Publisher Model ID、区域和退役安排须独立核实。

2）核心技术机制与 Breaking Changes

本次变化不只是替换字符串。Google 明确指出 Function Calling 协议与校验、thought_signature 验证、thinking_level 替代 thinking_budget、部分采样参数移除以及 Prefilled Model Turns 不再支持等兼容性风险。

旧参数示例（不是新模型迁移后请求）：

{
  "model": "gemini-2.5-pro",
  "generationConfig": {
    "thinkingConfig": {"thinkingBudget": 8192}
  }
}

不能把数字 8192 直接迁移成新 thinkingLevel；需按目标模型的官方枚举与结构处理。

Business Application
       -> Enterprise AI Gateway
       -> Old Model ID
       -> Provider Alias Resolver
       -> After 2026-12-01: New Model
             -> Thinking Schema
             -> Tool Validation
             -> New Pricing
             -> Potential Behavior Change

应同时记录 requestedModel 与 resolvedModel，防止自动别名迁移掩盖真实执行模型。

3）为什么有价值？技术与成本判断

这是确定的生产生命周期风险，优先级高于一般模型发布新闻。可能出现参数/工具请求直接报错、响应正常但结果行为变化、缓存和输入输出 Thinking 计费变化。Google 公布了目标模型的计费口径，但本期没有在相同地区、上下文及工具预算下获得可信的旧新价格与 P95 对照，因此不猜测降本百分比。

4）适用产品、业务场景和工程用途

影响 Gemini API 文本生成、Java/Spring Boot、Function Calling Agent、RAG、多模态理解、AI Coding、后台研究及用 Nacos 管理模型路由的微服务。未使用旧 ID 的项目只需记录生命周期，无需为了公告迁移。

5）对 Java、AI Gateway、Nacos 和分布式架构的帮助

应将 provider、requestedModel、resolvedModel、region、apiVersion、thinkingSchema、toolProtocolVersion、lifecycleStatus、rerouteDate、pricingPolicy、lastValidatedAt 分开管理。InterfaceClient.invoke(...) 等领域网关继续管理业务身份和权限，模型 Schema 变化由 Provider Adapter 处理，而不是侵入业务领域接口。

6）迁移步骤、命令与验收标准

PowerShell 5.1 本地扫描示例：

$patterns = @('gemini-2.5-pro','gemini-2.5-flash','thinkingBudget','thinking_budget','thought_signature')
Get-ChildItem . -Recurse -File -ErrorAction SilentlyContinue |
  Where-Object { $_.Extension -in '.java','.json','.yaml','.yml','.properties','.toml','.ts','.py' } |
  Select-String -Pattern $patterns -SimpleMatch

另需检查远程 Nacos、数据库模型配置、CI Secrets、云端应用。使用 20 条 Golden Tasks 覆盖 JSON、连续 Tool Calling、Thought Signature、文本和多模态请求，比较目标模型的 HTTP 400、工具结果、缓存、Token、费用与 P95。

验收标准：旧 Model ID 均进入迁移清单；新 Schema 通过验证；任务正确率达到业务门槛；费用可解释；12 月 1 日前完成生产切换。

7）优先级、迁移代价与结论

必看。生产系统必须在 12 月 1 日前完成受影响调用的迁移验证。 简单文本迁移代价可能较低；复杂 Agent Tool Calling、Thinking、多模态需充分回归。官方未保证新旧模型完全等价。

二、Anthropic｜Messages API Message Threads Beta：服务端短期会话

官方标题：Message threads｜发布：2026-11-02｜Beta Header：message-threads-2026-08-12｜状态：Beta｜优先级：必看

官方来源：Claude Platform Release Notes · Message Threads 开发指南。

1）内容是什么？版本与可用范围

Anthropic 为 Messages API 引入 Message Threads。传统多轮请求需反复提交完整历史；新功能把会话短期保留在服务端，后续只发送增量消息并引用上次 Response ID。支持 Claude API、Claude Platform on AWS、Google Cloud 上 Anthropic 托管模型和 Microsoft Foundry。处于 Beta，需要指定 Header；账户与云端实际权限仍应核对。

2）核心机制、请求 Schema 与状态约束

创建请求主要字段：

{
  "model": "claude-opus-5-5", "max_tokens": 1024,
  "messages": [{"role":"user","content":"查询一个测试订单"}],
  "thread": {"type":"create"}
}

下一轮继续：

{
  "model": "claude-opus-5-5", "max_tokens": 1024,
  "messages": [{"role":"user","content":"解释它的当前状态"}],
  "thread": {"type":"continue","previous_message_id":"<PREVIOUS_RESPONSE_ID>"}
}

两个 JSON 是核心字段示例，真实调用还需要鉴权、anthropic-version 及请求头：

anthropic-beta: message-threads-2026-08-12

Agent Request -> Thread Create -> Server-side Conversation
       -> New Message + Previous Response ID
       -> Thread Continue -> Model Response

状态约束：system 和 tools 只在 Create 提交，Continue 不可重复发送；模型、Thinking、Tool Choice、输出格式等固定字段不一致可能返回 thread_fingerprint_mismatch。MCP 服务器地址/Token 和 Container ID 并非全部自动存储，需按文档再次提供。Thread 是追加式结构；从旧 Response ID 分叉或修改历史需要新 Thread。对于 pause_turn，按文档发送空消息续跑，而不是插入新的用户轮次。

3）价值、性能、成本与隐私

减少完整对话历史重复上传、验证和 Tokenization 开销，有利于长会话的请求体大小和首 Token 延迟稳定性。但该功能不改变 Token 价格和 Rate Limits，不代表历史 Token 自动免费。最关键的治理限制：Message Threads 不符合 ZDR，也不符合 HIPAA 要求。 服务端采用加密短期内存，不写持久存储；Thread 在最后一次请求后约 5 分钟过期，数据最晚在最后使用后 1 小时删除。

4）适用业务场景

多轮 Coding Agent、连续领域问答、长工具链、自动研究和需要低传输开销的内部助手。ZDR/HIPAA 等严格合规业务不应启用这项 Beta，应沿用满足其政策的既有方案。

5）对 Java / Spring Boot / Nacos / AI Gateway 的帮助

Business Task State
       -> Local Execution Ledger
       -> Provider Thread Reference
       -> Anthropic Message Thread

本地账本仍需保存 taskId、previousMessageId、toolCallId、用户授权和幂等键。短期供应商 Thread 不能当企业业务数据库。Gateway 应将其作为可关闭的 Provider Capability，并对不符合数据政策的租户禁止使用。

6）教程、实践代码和验收

使用脱敏数据，比较普通完整历史请求与 Thread 五轮只读查询，模拟 Thinking/Tools 更改、Thread 过期、404 与网络中断；重建完整历史时不能重新执行已完成的写入工具。

Python SDK 简化示例：

import anthropic
client = anthropic.Anthropic()
thread = client.beta.messages.thread(
    model="claude-opus-5-5",
    max_tokens=1024,
    system="You are a read-only test assistant."
)
first = thread.send({"role":"user","content":"Describe a sample order."})
second = thread.send({"role":"user","content":"Summarize the order status."})

Java SDK 也有 Thread Helper，但具体类型与方法名要遵守对应已安装版本，不能照搬 Python 方法名。验收标准：续接正确；过期可恢复；MCP 授权不丢失；业务写入不重复；数据保留政策符合要求；P50/P95 与费用可复测。

7）优先级、兼容性与迁移判断

必看，仅适合数据保留策略允许的场景进行 Beta PoC。 验证 Beta Header、固定字段、SDK 版本、缓存和 Compaction；金融等有严格零保留要求的业务不可只为降低延迟而直接上线。

三、阿里巴巴 / Qwen｜Qwen Code 0.26.6 与 TypeScript SDK 0.1.27

官方发布日期：2026-11-02 UTC｜CLI：v0.26.6 正式版｜SDK：v0.1.27 正式版｜优先级：建议看

官方来源：Qwen Code v0.26.6 · TypeScript SDK v0.1.27。

1）内容是什么？准确版本与功能

Qwen Code 0.26.6 的 Release Notes 标记 No known breaking changes。配套 TypeScript SDK 0.1.27 捆绑 CLI 构建版本 0.26.6。

模块 具体变化
Web Shell 会话活动视图区分审批、输入、错误、运行中、未读任务
模型观测 请求成功率、输出速度、首 Token 延迟及模型级失败信息
Workflow Web Shell 的 Workflow 控制和工具不可用提示
Agent Runtime 实验性 Unified Agent Loop 扩展到更多 ACP Turn
Hooks Headless 模式支持 prompt.submit Hooks
MCP 避免重复工具名遮蔽整个 MCP Server 的其他工具
Agent 恢复 缺少子任务执行证据时不能错误补全历史状态
Windows 更新时先停止绑定的运行时，减少文件锁导致的升级失败
外部模型上下文 修复 Kimi K3 Model ID 被误识别成小上下文版本

还改进了 Web Shell 审批文本的控制字符与双向字符处理，避免屏幕显示与审批意图不一致。

2）核心技术机制与关键知识点

重要方向是执行证据优先于状态推断：

Parent Agent -> Child Agent -> Tool Call
                    |             |
                    v             v
               Execution Ledger / Result Delivery
                             |
                             v
                      Reconciliation
                       /        \
                 Evidence     No evidence
                  Apply       Unknown/Review

MCP 同名工具冲突应只影响冲突名称，而不能让独立工具全部消失。模型指标区分 TTFT、输出速度和失败率，优于只显示总 Token。Headless Prompt Hook 可在提交前检查输入，但不能替代业务服务端授权。

3）为什么有价值？性能与证据边界

主要是增强 Agent 可靠性、状态追溯、错误定位与成本诊断。UI 展示输出速度不意味着模型推理能力或 P95 自动改善；没有可推广到所有环境的官方性能提升百分比。

4）适用业务场景

多模型 AI Coding、企业 Web Shell、ACP、MCP、Skills、Hooks、PR Review、Headless CI、Managed Agent、Windows 开发环境。

5）对 Java / Spring Boot / Gateway 的帮助

建议分别保存 taskId、agentSessionId、父子任务、工具执行证据、审批决定、Model Usage 与最终业务状态。即使 Agent 恢复后预期某项操作已经执行，也必须依赖业务服务记录确认，不能凭模型推断将订单更新为成功。K3 上下文识别修复是客户端识别 Model ID 的变化，不是 Moonshot 在当天发布新的 Kimi 权重。

6）升级、测试与验收

PowerShell 5.1：

qwen --version
where.exe qwen
node --version
npm install -g @qwen-code/qwen-code@0.26.6

升级操作仅建议在隔离测试环境先执行。验证 Headless Hooks、MCP 同名工具、子任务中断恢复、Windows 文件锁、Workflow 和模型 TTFT 统计。TypeScript 应单独核对 SDK 0.1.27 与嵌入式 CLI 一致性。

验收标准：未授权执行为零；子任务状态有证据；MCP 冲突不遮蔽其他工具；中断后恢复不重复写入；观测指标能对应真实模型请求。

7）优先级、Breaking Change 与迁移代价

建议看。使用 Web Shell、Managed Agent、Hooks、MCP 的开发者值得回归后升级。 官方没有列出已知 Breaking Changes，但自定义插件和第三方模型配置仍需回归。此客户端版本不代表基础模型价格或许可证更新。

四、Moonshot AI / Kimi｜Kimi Code 2.5.0 Canary 的 Agent 运行时实验

发布日期：2026-11-02｜版本：2.5.0-canary.20261102033430-40590f6｜状态：Pre-release｜优先级：建议看（普通用户可跳过）

官方来源：Kimi Code Canary Release。

1）内容是什么？

本次 Canary 更新包括：ACP 请求在启动完成前排队；合并不同工作区目录的 Skills；避免归档会话在索引刷新前重新出现在活动列表；按文件夹范围获取 Git Status；将工具声明与实际执行解耦；调整 Agent Core v2 的 Compaction 测试预算。这是实验性客户端更新，非新的 Kimi 模型发布。

2）核心技术机制

Tool Discovery / Disclosure
       -> Permission Gate
       -> Tool Execution

模型可以看到工具，不代表它获得权限。ACP 初始化、会话索引刷新和工具真正执行属于不同的状态机。

3）为什么有价值？

多工作目录环境下 Skills 发现和权限容易混淆。分离声明与执行，有助于防止错误授权；但 Canary 没有稳定部署承诺，也没有独立统一的性能改进数据。

4）适用业务场景

多工作区编码、ACP 客户端、多 Agent、Skills、Git 自动化、Agent Runtime 架构研究。

5）对企业架构的帮助

能力至少区分 DISCOVERABLE、AUTHORIZED、EXECUTED。服务端根据用户、租户、资源重新判权；工具目录不能充当访问许可。

6）实践步骤与验收

用隔离仓库测试两工作区 Skills、ACP 初始化前请求、工具拒绝和子任务恢复。验收标准：初始化前不错误执行；拒绝的工具无副作用；归档会话不恢复为活动任务。

7）优先级与风险

建议看，普通用户保持 2.4.1 Stable。 不把 2.5.0-canary 误标为正式版，也不从客户端发布推测新的 Context、Thinking 或价格。

五、Google｜Gemini CLI 11 月 2 日 Nightly

1）内容及来源

Nightly 是开发回归通道，不保证适合生产部署，也不等于 Gemini API 发布了新基础模型或新协议。

3）价值及限制

可供定位 Windows、终端、MCP 或长期任务问题；不是性能改善或价格变化证据。

4）适用场景

Gemini CLI 研发测试、Windows Terminal、CI、MCP、插件、Agent Coding。

5）对企业架构的帮助

生产明确区分 stable、preview、nightly，避免自动将实验包写入共享环境。

6）测试与验收

PowerShell 检查 gemini --version；只在隔离项目启用 Nightly，固定测试任务，验证工具权限、插件、配置迁移与回滚。验收标准：无新增安全违规和关键任务回归，构建通道可以审计。

7）优先级

可跳过，Stable 基线保持 0.66.0。 未核实到与该 Nightly 绑定的新 Context、Thinking、定价或 API Breaking Change。

十、综合工程判断

本期核心是模型生命周期管理与 Agent 状态管理日益成为企业 AI 平台底座。Google Gemini 2.5 退役说明透明别名迁移可能保留 HTTP 200 却改变协议、模型和账单；Gateway 必须维护版本与能力矩阵，而不只是 Base URL。Anthropic Threads 说明长会话性能可能依赖短暂服务端状态，也带来过期、恢复、隐私和字段限制，不能代替本地业务账本。Qwen Code 对恢复、工具发现、Hooks 和观测的强化，让 Agent Runtime 更接近可审计的业务执行系统。
