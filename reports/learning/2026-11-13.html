01Agent Harness · 智能体运行框架／执行编排系统

IPA /ˈeɪ.dʒənt ˈhɑːr.nəs/ ｜ 诶真特 · 哈内斯 ｜ 谁组织模型与工具的持续执行？

01 · 一句话理解

Agent Harness 是让大模型从“回答问题”变成“持续执行任务”的运行系统。大模型根据上下文提出下一步行动；Harness 管理运行状态、工具调用、执行结果、审批、失败以及终止条件。它不是某个模型，也不是一段万能提示词。

02 · 为什么需要它／解决什么问题

例如用户要求“修复订单接口返回 500 的问题”。单次模型回答只能给出建议；完成修复往往还要找入口、读文件、定位异常、改代码、跑测试、追踪失败并提交证据。

困难有三层：模型的叙述不等于实际执行，说“测试通过”不代表执行了测试；任务需要连续状态，应保留已读文件与失败记录；工具有真实副作用，Shell、编辑器和网络动作可能修改文件或外传数据。Harness 将它们放进可追踪、可控制的运行过程。

03 · 核心原理和工作机制

典型运行过程分六步：① 接收任务并保存目标、工作目录、约束；② 组织用户需求、文件、工具定义与执行历史等上下文；③ 模型提出下一步行动；④ Harness 在执行层检查权限并调用工具；⑤ 捕获输出、错误、退出码与文件变化反馈模型；⑥ 决定继续、重新诊断或结束，并服从超时、成本和次数限制。

观察 → 选择行动 → 执行 → 反馈 → 再判断 是核心循环。模型层判断“应该做什么”，执行层约束“真正允许什么”，两者必须分离。OpenAI 官方关于 Codex Harness 的说明区分了模型、运行循环、工具、会话状态与运行环境。

04 · 贴近日常或软件开发的类比

把 Agent 想象成工程师，Harness 像项目经理与任务系统：工程师判断先查日志还是读代码；系统记录进度、安排操作入口、保留验收结果、执行审批。类比的边界是 Harness 并不必然像人类经理一样理解全局：一个很简单的工具循环也可称为 Harness，复杂产品才会实现更多控制能力。

05 · 一个真实 AI 场景示例

某团队希望 Coding Agent 修复订单接口空指针：只修改对应服务和测试，不进行远程提交，测试失败必须解释原因。

任务开始 → 读取服务代码 → 定位空指针 → 修改 → 运行测试
  ↓ 如果测试失败：读取错误 → 检查修复假设 → 重新修改和测试
  ↓ 如果验证达到条件：记录 Diff、真实测试结果、剩余风险

测试命令没有成功运行时，交付结果应写“未验证”，不能凭模型的文字推断成“测试通过”。

06 · 与易混淆概念的区别

概念主要职责
大语言模型生成内容、判断下一步、提出工具调用
Agent Harness会话、行动循环、工具调度、执行反馈
Agent Skill某一类任务的可复用说明与资源
MCP与外部工具、资源的协议化连接
AI Coding Agent模型、Harness、工具与交互组成的完整编程助手

Harness 可能嵌在 CLI、IDE 或服务端中，不一定是一套独立安装包。

07 · 实际工作中如何使用

设计自己的最小 Coding Agent 时，先写出运行契约，而不是急着接十几个工具：输入为任务、仓库、允许范围；状态为目标、已完成步骤、失败原因；工具至少能读取、搜索、编辑和测试；边界包括审批、禁用动作、超时和最大行动次数；输出必须写明代码变化、测试证据及剩余风险。即使只有一个模型和三个工具，也应把模型建议和真实工具结果分开记录。

08 · 常见误区

误区一：认为模型越强越不需要 Harness。模型再强也不能替代真实文件或网络权限。误区二：模型生成了完整计划便能保证所有步骤执行成功，实际上工具和环境都可能失败。误区三：失败时无限自动重试；没有终止条件可能反复改坏文件、持续消耗资源，必须设置停止与人工介入出口。

09 · 一个思考题

Agent 修改完代码后，测试进程异常退出，没有有效结果；模型却回复“所有测试通过”。这是模型判断错误、Harness 设计问题，还是两者都有？为了阻止这种交付，运行系统至少应该保留哪些原始证据？

02Task Decomposition · 任务分解

IPA /tæsk ˌdiː.kɑːm.pəˈzɪʃ.ən/ ｜ 塔斯克 · 迪康珀兹伊申 ｜ 怎样把模糊需求变成可验收的小任务？

01 · 一句话理解

Task Decomposition 是把一个模糊的大目标转换成可执行、可验证、依赖关系明确的小任务。重点不是把一句话硬拆成十句，而是为每一步定义输入、行动、输出和完成条件。

02 · 为什么需要它／解决什么问题

“优化接口性能”实际上隐含许多问题：究竟是慢 SQL、网络、线程锁竞争还是内存不足？优化会否改变业务行为？用什么数据证明性能改善？不分解就直接改异步调用，可能忽视真正的数据库瓶颈。分解可以缩小不确定性，让每次工具行动都对应明确目的。

03 · 核心原理和工作机制

任务分解的实用表示是依赖图：A 复现问题 →（B 阅读代码，C 检查测试覆盖，可在彼此独立时并行）→ D 最小修复 → E 运行测试与验收。

复现失败输入调查代码 / 测试覆盖实施最小修复测试、验收

一项合格的子任务写清“输入 → 允许行动 → 预期产物 → 验收条件”。例如：“读取最近一次异常日志并输出调用堆栈与对应代码行；本步骤不改文件”。执行中如果发现新证据指向下游服务，必须调整计划并留下依据，而非机械走完旧清单。

04 · 贴近日常或软件开发的类比

做饭时先洗菜、切菜、烹饪、装盘；洗菜和准备调料可并行，但必须准备好食材才能做菜。软件任务更加不确定：像检查出食材变质一样，若调查得到了新的根因，应改变原计划。类比能解释依赖关系，却不能替代系统实际的故障诊断。

05 · 一个真实 AI 场景示例

Spring Boot 接口偶发 HTTP 500。一个实际可用的调查计划包括：① 收集请求与异常堆栈，尝试复现；② 跟踪 Controller、Service、Repository 相关调用；③ 比对正常与异常输入，形成假设；④ 新增先失败的回归用例；⑤ 只修改必要代码；⑥ 运行目标与相关回归测试，附交付证据。这比“一口气重写 Service”更容易定位问题与责任。

06 · 与易混淆概念的区别

任务分解不只是“写代码→测试→提交”的待办清单，因为后者没有说明步骤依赖和验收。任务分解也不是多 Agent 并行：只有边界明确、资源不冲突的任务适合并行。它也不等于写很长的计划，两步小任务没有必要产生二十个规划节点。

07 · 实际工作中如何使用

可要求 Coding Agent：“先调查并列出不超过五个子任务。每项注明输入、预期输出、是否改文件和完成条件；调查后再确定修复。任何远程写入必须另行授权。”每项状态可以是 pending／running／passed／failed，但 passed 应由可查证的产物支持，不应由模型自行宣布完成。

08 · 常见误区

误区一：拆得越碎越好，实际上过度拆分增加协调与状态开销。误区二：认为所有子任务都可交给多个 Agent 同时编辑，可能发生冲突或互相覆盖。误区三：计划生成就不能变，现实中应随证据修正，只是修正原因要留痕。

09 · 一个思考题

三个 Agent 分别修改 Controller、Service 与测试。执行中发现 Controller 和 Service 都需要变更同一个公共 DTO。你会怎样调整依赖与工作区分工？哪些可以并行，哪些应该串行，为什么？

03Git Worktree · Git 工作树／独立检出目录

IPA /ɡɪt ˈwɝːk.triː/ ｜ 吉特 · 沃克特里 ｜ 在不打扰主工作区的情况下修改代码

01 · 一句话理解

Git Worktree 允许一个 Git 仓库同时拥有多个代码工作目录。不同任务可以使用独立检出目录，而不必反复切换主工作目录的分支。这是多任务开发和 Coding Agent 并行工作的实用基础设施。

02 · 为什么需要它／解决什么问题

你正在 IntelliJ 修改订单服务并有未提交内容，另一个 Agent 想修复支付模块。若二者直接共享同一目录，Agent 可能覆盖你的改动、把你的修改误当自己的结果、在错误分支上测试，或者把两个任务的变化混成一个提交。Worktree 的价值是保留你当前工作目录，同时为另一任务检出独立的一套文件。

03 · 核心原理和工作机制

Git 保存提交、对象和引用；工作目录是实际编辑的文件。多个关联工作树共享底层 Git 数据和部分配置，却各有自己的工作文件、暂存索引和检出状态。

主工作树你的未提交开发、当前检出文件
Agent 工作树另一个目录、另一任务的文件变化

三个事实：① Worktree 不等于独立仓库，共享部分历史和引用；② 新工作树不会自动包含主目录尚未提交的修改，基准提交要明确；③ Worktree 不是操作系统沙箱，有权限的进程仍可能访问其他目录或网络。

04 · 贴近日常或软件开发的类比

像给两位设计师各自发一套独立图纸，但共同使用一个版本档案室。个人图纸上暂时互不覆盖，但未来合并仍可能冲突，且每人仍可能接触共享资料。Worktree 只解决部分工作文件干扰，不自动提供隔绝一切资源的安全边界。

05 · 一个真实 AI 场景示例

开发者在主工作树完成订单业务，Coding Agent 在关联工作树修复另一个模块。Agent 在其目录读文件、修补代码、运行测试并生成 Diff；开发者随后审查是否合并。这避免中间变更直接污染主工作目录。但若 Agent 具有本机其他目录的权限，仍可越出 Worktree，因此要结合权限策略或沙箱。

06 · 与易混淆概念的区别

方式差别
git switch同一工作目录切换检出状态
git clone另建仓库副本，通常有独立仓库元数据
git worktree同一个仓库关联多个检出目录，共享对象与引用
Docker / OS Sandbox可限制文件、进程、网络访问，取决于隔离配置

07 · 实际工作中如何使用

先确认当前仓库已有初始提交，然后使用官方 Git 命令：

git worktree list
git worktree add -b agent-fix ../agent-fix
git worktree list
git -C ../agent-fix status --short

给各任务分配唯一目录与分支，确认 Agent 使用的工作目录及基准提交。命令来自 Git 本身，不需要依赖某款 Coding Agent 的额外扩展。

08 · 常见误区

误区一：一 Agent 一 Worktree 就完全安全——实际上不是沙箱。误区二：会自动同步主工作树的未提交修改——不会。误区三：完成就可强制删除——未跟踪文件或未提交修改可能有价值。Git 通常拒绝删除不干净的工作树，不建议无条件使用强制删除。

09 · 一个思考题

主工作树有一项未提交的接口签名更改；Agent 工作树从旧提交创建，修复后测试全通过。为什么这仍不能说明修复可直接并入当前主工作树？应该如何验证兼容性？

04Unified Diff · 统一差异格式

IPA /ˈjuː.nɪ.faɪd dɪf/ ｜ 尤尼法伊德 · 迪夫 ｜ 把代码变化变成可审查的补丁证据

01 · 一句话理解

Unified Diff 用结构化文本描述修改前后的差异。它让人和工具识别哪些内容被删除、哪些内容被新增以及变更发生的位置，是代码审查、补丁应用和 Agent 交付的桥梁。

02 · 为什么需要它／解决什么问题

“我修改了三个文件”只是一个结论，远不足以评估风险。真正需要核查的是：改了哪里、是否改动授权范围外的文件、是否误删异常处理、有没有补充测试，以及变更能否应用到目标版本。相比重新阅读整个文件，Diff 将注意力集中于变化本身。

03 · 核心原理和工作机制

把 return a - b 改成 return a + b，统一差异可写为：

diff --git a/add.py b/add.py
--- a/add.py
+++ b/add.py
@@ -1,2 +1,2 @@
 def add(a, b):
-    return a - b
+    return a + b

--- 是旧文件，+++ 是新文件；@@ -1,2 +1,2 @@ 表示两侧的行位置与范围；以减号开头的行被删除，加号开头的行被添加，前导空格是保留上下文。一个修改片段叫 hunk（差异块）。上下文既利于人工审查，也帮助工具定位应用位置。git apply --check 可以检查补丁是否适用，但不实际写入。

04 · 贴近日常或软件开发的类比

合同里只更改付款日期，法务给出带修订痕迹的合同而不是不标注变化的全文。Diff 与之相似，不过 Git 的差异格式可以由工具解析，用于检查或应用修改，而不仅仅给人观看。

05 · 一个真实 AI 场景示例

一个 Coding Agent 修改价格服务的舍入算法。交付时，除了描述“金额计算已修复”，还应附改动文件清单、统一差异、影响的业务分支、关联测试及未解决问题。如果 Diff 显示 Agent 顺便移除了异常日志，评审者就能立即追问或拒绝。

06 · 与易混淆概念的区别

Diff ≠ Commit：Diff 是变化表达，Commit 则记录版本快照与元数据。Patch 与 Diff 有交集：补丁通常是可供应用的修改内容，阅读型 Diff 未必能直接应用。git diff --check ≠ git apply --check：前者主要检查差异中的空白问题；后者检查给定补丁能否应用；两者都不验证业务正确性。

07 · 实际工作中如何使用

git diff                      # 当前未暂存的文件差异
git diff --check              # 检查常见空白问题
git status --short            # 同时检查未跟踪文件
git diff --output=change.patch
# 在未应用补丁、基准匹配的目标工作树中：
git apply --check change.patch

避免在已经包含相同修改的目录直接调用 git apply --check；它可能因内容已被修改而失败。普通 git diff 也不会自动显示未跟踪文件，需同时审查 git status。

08 · 常见误区

误区一：Diff 小就安全，一行权限判断或金额公式也可能造成重大问题。误区二：git diff --check 通过就等于代码正确，它并非语义验证。误区三：补丁能应用就等于可以发布，这仅说明文件匹配等条件基本满足，并没有验证编译、业务和副作用。

09 · 一个思考题

Agent 从旧基准提交生成补丁，其他开发者随后改了同一段代码。若 git apply --check 失败，应该直接覆盖最新版，还是重新读取目标版本并分析冲突？请解释理由和风险。

05Verification Loop · 验证闭环

IPA /ˌver.ɪ.fɪˈkeɪ.ʃən luːp/ ｜ 维瑞菲凯申 · 卢普 ｜ 把“修改过”变成“有证据表明达到目标”

01 · 一句话理解

Verification Loop 是让 Agent 在做出修改后，利用实际检查结果判断目标是否达成；未达成时根据证据修正或停止。“已经修改”和“经过验证”必须是两个不同状态。

02 · 为什么需要它／解决什么问题

模型可能写出语法正确、看似合理但业务错误的代码；还可能通过局部测试，却破坏其他接口约定。典型风险包括能编译但计算错误、单元测试通过却集成失败、没有覆盖原始失败输入，以及根本没有跑测试却报告为成功。验证闭环要求成功与失败都有实际可核对的依据。

03 · 核心原理和工作机制

一个基本闭环是：① 执行真实修改；② 检查影响范围、Diff、语法、格式；③ 运行目标测试与相关回归测试；④ 保存命令、输出、退出码；⑤ 通过既定标准则交付，否则读取失败证据、修正假设并有条件地重试。

修改代码静态检查运行测试分析结果

例如函数必须满足 add(2,3) == 5，真正的验证依据是断言执行结果。单个输入通过仍不代表负数、零或其他边界都正确。重试应有次数、时间和相同失败的终止规则，不能无限“改到绿灯”。

04 · 贴近日常或软件开发的类比

工厂加工零件后，工人说“我按规范操作”并不是验收，必须测量。量具若只测长度，则不能证明强度达标；测试同样只覆盖被观察的属性和输入。通过测试说明通过了已执行的测试，不保证不存在全部缺陷。

05 · 一个真实 AI 场景示例

订单接口曾因空值返回 500。Agent 修复后至少应检查三类输入：原始失败案例现在是否得到符合约定的响应；正常业务案例是否仍正确；边界案例（空订单号、缺失字段、下游异常）是否仍有合理行为。只跑第一类就宣布完全解决，风险依然很大。

06 · 与易混淆概念的区别

Verification Loop 不只是重复跑测试，而是包含失败解释、假设调整和停止判断。单元测试关注局部逻辑，集成测试关注组件协作；测试通过不代表获准合并或上线；模型自评不是独立测试的替代品。应记录工具实际产生的退出码和测试日志，而非模型的主观判断。

07 · 实际工作中如何使用

要求 Agent 交付统一证据：目标、修改文件、Diff、运行的测试命令、各命令退出码、实际通过案例、失败/未运行案例、剩余风险、是否允许合并或发布。若缺少依赖、权限不足或测试超时，应标为“未验证/失败”，不得跳过。重试要说明上次失败与本次改动的对应关系。

08 · 常见误区

误区一：绿色测试意味着绝对正确，实际测试用例可能覆盖不全。误区二：模型声称自查过就可以取代自动验证，模型判断不能替代真实执行结果。误区三：不断重试一定会越来越接近成功；根因假设错误时可能越改越乱，必须设置诊断与停止策略。

09 · 一个思考题

Agent 三次修复均通过自己新增的测试，真实业务问题却仍存在。最可能是任务分解、测试设计、执行反馈中哪些环节有缺口？你会如何改造验证闭环，让它直接检验原始用户问题？

今日串联 · 五个知识点如何组成完整知识链？

用户需求 → Harness 建立任务会话 → 任务分解 → 创建独立工作树 → 修改代码 → 生成 Diff → 执行测试 → 依据真实结果修正或交付。

  1. Agent Harness：谁负责组织执行？维持工具循环、状态记录、反馈和停止条件。
  2. Task Decomposition：应该先做哪些事？把复杂需求变成依赖关系清楚、能验收的子任务。
  3. Git Worktree：在哪里组织修改？使用独立目录，减少与开发者现有改动相互干扰。
  4. Unified Diff：怎样精确表达修改？保留可审查、可检查的差异和补丁。
  5. Verification Loop：怎样证明修改有效？真实运行测试并记录证据，失败时有边界地修正或停止。

昨天的项目规则、Skills、MCP、Hooks 与权限策略可以参与这条链，却不能自动把 Worktree 变成安全沙箱，也不能替代实际测试。可靠 Agent 的标准不是“调用了多少工具”，而是每次行动的边界和最终证据。

今日微型练习｜从错误函数到隔离修改和验证

目标：建立本地 Git 仓库，为模拟 Coding Agent 创建单独 Worktree，修复一个有意写错的 Python 加法函数，产生统一差异并验证补丁和实际测试。

环境：Windows PowerShell 5.1 或 7.x、Git 和 Python 3。无需真实 AI Agent、付费模型、GitHub 凭证或外部网络。

输入：原始 add.py 的 add(a,b) 错误地返回 a-b；修复后应满足 add(2,3)==5 与 add(-2,1)==-1。

操作步骤与原因

  1. 创建一个临时仓库。脚本用 [Guid]::NewGuid() 生成唯一路径，写入错误函数并创建第一次本地提交，确保 Worktree 有可检出的基准版本；示例邮箱 example.invalid 不是真实账户。
  2. 建立独立工作树。git worktree add -b agent-fix 在新的目录和分支检出代码，不覆盖原工作目录。
  3. 先做失败测试，再修代码。初始 add(2,3)==5 断言应失败，这证明要解决的问题确实存在；随后把减号改成加号。
  4. 验证和审查。运行 git status --short、git diff、git diff --check 和两个 Python 断言，观察实际退出码与输出。
  5. 生成并检查补丁。用 Git 自己生成 change.patch 避免 PowerShell 5.1 重定向的编码问题；在未经修改的主工作树运行 git apply --check，最后查看主目录原始文件，证明它没有被覆盖。

PowerShell 5.1 / 7.x 示例代码

$base = Join-Path $env:TEMP (
    'ai-agent-lab-' + [Guid]::NewGuid().ToString('N')
)
$work = $base + '-agent'
New-Item -ItemType Directory -Path $base | Out-Null
Push-Location $base
git init
@('def add(a, b):', '    return a - b') | Set-Content -Encoding ASCII add.py
git add add.py
git -c user.name="AI-Lab" -c user.email="lab@example.invalid" commit -m "lab baseline"
Pop-Location

git -C $base worktree add -b agent-fix $work
git -C $base worktree list
Push-Location $work
# 预期失败：当前实现是减法
python -c "from add import add; assert add(2,3) == 5"
# 模拟 Agent 修复
@('def add(a, b):', '    return a + b') | Set-Content -Encoding ASCII add.py
git status --short
git diff -- add.py
git diff --check
python -c "from add import add; assert add(2,3) == 5; assert add(-2,1) == -1; print('2 tests PASS')"
git diff --output="$base\change.patch" -- add.py
git -C $base apply --check "$base\change.patch"
git -C $base show HEAD:add.py
Pop-Location

预期结果

检查项预期现象
初始断言失败；确实复现了减法错误
git worktree list列出主工作树和 Agent 工作树
git diff- return a - b / + return a + b
git diff --check没有差异格式或常见空白问题
修复断言输出 2 tests PASS

故障与风险检查：若 python 命令不存在，Windows 可能需要用 py -3；若 Worktree 创建失败，先确认有初始提交、分支与路径未重复。该练习完全位于临时仓库，不调用真实网络或远程推送，不强制删除工作树。git diff --check 不验证业务功能，两个断言的通过也不等于生产质量。

验收标准：能够实际得到基线失败、修复后两个断言通过、一份可检查补丁，并证明主工作树未被本次修改覆盖；还应能解释 Harness、任务分解、Worktree、Diff、验证闭环各自的责任及局限。

自我迁移：若真实任务改为修复一个 Spring Boot 接口，应该把哪个 Python 断言替换为接口回归测试？又该如何补充至少一个正常请求与一个边界请求？
