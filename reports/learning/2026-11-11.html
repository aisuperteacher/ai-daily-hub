LESSON 01/05数据质量 / 测试覆盖

Golden Dataset：黄金评测集

英语主词条：Golden Dataset　IPA：/ˈɡoʊl.dən ˈdeɪ.tə.set/　中文近似：勾尔登 · 得塔塞特　含义：黄金评测集（发音播放器见页面顶部）

1. 一句话理解

黄金评测集是一组经过明确标注和审核、具有预期结果或判定准则的代表性任务样本，用来稳定比较 AI 应用不同版本的质量。 它不是随便找几个问题问模型，而是让每次修改都接受相同规则的检验。

2. 为什么需要它？解决什么问题？

普通软件的函数常有确定输入输出，例如 add(2,3) 必须得到 5。AI 自然语言输出可能存在多种正确措辞：不同版本的回答看起来都不错，却可能遗漏重要业务条款。随手测试容易出现三种偏差：今天与昨天使用的题目不同、只挑容易的案例、只关注回答流畅度而忽略业务错误。黄金评测集提供相对稳定的基准。

3. 核心原理和工作机制

每条样本尽量同时记录输入、预期结论、依据、风险标签和版本信息：

case_id: C04
scene: 跨境退款
input: 4800元跨境企业退款是否需要财务复核？
expected: 财务复核
reason: 模拟制度第2条
risk: 跨境例外 / 高风险
policy_version: policy_v1
review: 已人工核对

建立流程为：①定义任务和判断标准；②收集典型、边界、例外、失败案例；③为每条写明标准答案或评分规则；④请领域专家复核争议案例；⑤按风险标签分层并记录版本；⑥将开发调试样本与保留验证样本适当分离。对开放式问题可以分别评判结论、证据、条件完整性，而不强求固定的一个句子。防止把保留测试题反复用于优化而造成评测过拟合。官方数据集与评测方法参见文末 OpenAI 与 LangSmith 文档。

4. 贴近日常或软件开发的类比

它相当于软件开发的回归测试套件：修复新问题时仍要确认老功能没有坏掉。但传统单元测试常可直接比较数值，AI 回答可能需要结构化规则、专家评价或受约束的模型评审。类比不能理解成所有回答都有唯一字符串答案。

5. 一个真实 AI 场景示例

模拟制度：普通退款 ≤5000 元走普通审批；>5000 元财务复核；跨境退款不论金额均需财务复核；金额无效或关键字段缺失时转人工。

样本 输入 预期
C01 普通退款 2000 元 普通审批
C02 普通退款 5000 元 普通审批
C03 普通退款 6000 元 财务复核
C04 跨境退款 4800 元 财务复核
C05 跨境退款 100 元 财务复核
C06 普通退款 0 元 转人工
C07 金额缺失 转人工
C08 退款类型未知 转人工

C04 与 C05 是关键例外，不应被大量普通简单题掩盖。以上业务制度完全为教学虚构。

6. 与易混淆概念的区别

  • 训练集用于优化模型或系统参数；评测集用于检验性能，应控制交叉污染。
  • 一般测试题可能未经审核、覆盖不均；黄金评测集应有清晰预期、依据、版本与复核记录。
  • 线上日志说明发生过什么，却不天然拥有正确答案。
  • 公开模型基准测试的是既定题目，不保证与你的企业业务一致。

7. 实际工作中如何使用

可以建 eval_cases.json，包含 case_id、问题、期望结论、风险级别、制度依据和版本。模型、提示词、RAG 配置或工具逻辑变化后，使用相同的冻结样本回归测试。记录模型、提示词、知识库、评测脚本版本和运行日期；制度变更时更新标准答案并保留旧版历史。

8. 常见误区

  1. 题目越多就一定越可靠：错误。关键风险的覆盖、样本代表性和审核质量更重要。
  2. 标准答案永远不变：错误。制度与业务规则可能更新，应保留时间和版本。
  3. 在训练中反复使用评测样本不影响可信度：错误。这可能造成数据泄漏或测试过拟合。
  4. 公开排行榜分数高，企业场景一定好：没有这种保证。

9. 思考题

100 道题里有 95 道普通题、5 道高风险例外题。模型正确回答全部普通题，却错过所有例外题。是否应该上线？请分别从总体分数与业务事故代价两方面解释。

LESSON 02/05业务风险 / 准入条件

评测指标与质量闸门

1. 一句话理解

质量闸门是一组预先定义的发布条件：只有质量、安全、延迟、成本等要求达到必要水平，新版本才可以进入下个阶段。 它回答“能否上线”，而不是只展示“模型得了多少分”。

2. 为什么需要它？解决什么问题？

一个新模型整体正确率可能从 92% 增至 95%，但错题集中在权限、跨境退款和财务审批等关键路径。平均分更高，不意味着业务风险更低。必须把总体表现、关键错误、成本与稳定性分开评估。

3. 核心原理和工作机制

可以组合这些指标：

  • 总体准确率 = 正确样本数 / 样本总数。
  • 关键例外召回率 = 正确认出的关键例外数 / 全部关键例外数。
  • 证据支持率 = 关键结论确实受到所引用证据支持的比例；“附了引用”不等于支持。
  • 工程指标：未授权工具调用、隐私违规、P95 延迟、请求成本与服务错误率。

例如教学用闸门：总体准确率 ≥95%；关键例外召回率 100%；关键安全违规 0；P95 ≤5 秒；成本不超预算。以上阈值不是通用生产标准，真实阈值需要结合危害、样本量、置信度及服务目标定义。

只有 8 条样本，即使全部答对，也不能得出真实准确率 100% 的统计结论；高风险场景通常需要更多样本、分层分析与人工复核。

4. 贴近日常或软件开发的类比

汽车出厂检查不能只看音响与外观而忽略制动系统。AI 输出流畅类似体验指标，审批例外不出严重错误类似安全底线。类比的边界是：真实业务风险和错误严重性无法完全简化成一个“总分”。

5. 一个真实 AI 场景示例

对于知识点一的八条模拟样本，旧版本全部正确；候选版本错误地把跨境退款按普通金额阈值处理，导致 C04、C05 出错：

总体正确率：6/8 = 75%
跨境例外召回：0/2 = 0%
关键错误：2
质量闸门：BLOCK（禁止进入下一阶段）

这组结果是本地规则函数的预期教学模拟，不是实际大模型的表现。比较新旧版本时必须在同一批用例上运行，以避免样本不一致误导结论。

6. 与易混淆概念的区别

  • 分数描述一个指标的表现；闸门决定是否准入。
  • 模型辅助评分可能存在自身偏差，不等于事实裁决。
  • 人工复核适合高风险或争议案例，但成本较高。
  • 确定性规则引擎适合金额、权限等硬性条件，与模型协作但不能被平均分替代。

7. 实际工作中如何使用

在持续集成或发布流水线中加入离线回归评测，输出整体成绩、分风险类别成绩、失败样本和与上一稳定版本的差异。关键业务错误单独设置阻断条件；非确定性输出重复测试、控制可控制的参数并报告波动，避免把单次评分当作绝对事实。

8. 常见误区

  1. 一个总体指标覆盖所有风险：错误；安全、质量、延迟、成本需分开。
  2. 让模型给自己评分就一定客观：错误；评分器也需测试。
  3. 小样本零错误等于线上零风险：错误；可能是覆盖不足。
  4. 测试完成即可忽略生产监控：错误；真实输入可能变化。

9. 思考题

新版本把普通问题准确率提高 5 个百分点，却产生一次未经授权的数据库写入行为。质量闸门如何设计，才能确保总体提分不能掩盖这类严重违规？

LESSON 03/05受控流量 / 无副作用

Shadow Testing：影子测试

英语主词条：Shadow Testing　IPA：/ˈʃæd.oʊ ˈtes.tɪŋ/　中文近似：沙斗 · 泰斯廷　含义：影子测试（发音播放器见页面顶部）

1. 一句话理解

影子测试把经过授权与隐私处理的代表性请求复制给候选系统，正式系统继续回答用户，而候选结果只用于比较。 它是接近真实输入条件的验证手段，不等于真实灰度上线。

2. 为什么需要它？解决什么问题？

离线用例覆盖不了所有错别字、长文本、缺失字段、混合语言和复杂会话。影子测试允许你观察候选系统如何处理有代表性的真实输入形态，但在正式切换前不改变用户获得的答案。

3. 核心原理和工作机制

概念链路：

                     ┌── 正式V1 ──→ 用户接收的结果
授权请求 ──受控复制───┤
                     └── 候选V2 ──→ 仅记录候选结果 → 评估比较

必须满足三项保障：①候选输出不进入正式用户响应；②候选工具运行严格隔离，不能触发真实支付、写库、短信、邮件等副作用；③流量复制遵循授权、脱敏、访问控制和数据留存要求。仅仅丢弃候选的文字答案，不表示工具调用没有执行。Google SRE 将相关流量复制思想称为 teeing，并指出共享缓存和后端会引入干扰。

4. 贴近日常或软件开发的类比

两位客服同时阅读同一咨询：正式客服回复客户，候选客服只填写自己的判断供质检比较。候选客服不能私下给客户退款。类比边界：AI Agent 可以调用真实工具，所以必须在技术执行层面隔离副作用，而不是仅口头要求不要操作。

5. 一个真实 AI 场景示例

模拟请求“4800 元跨境退款是否复核？”：

正式 V1：需要财务复核；依据跨境例外条款。
候选 V2：不需要；因为金额没有超过 5000 元。
用户实际看到：只看到 V1 的回答。
质检系统记录：V2 漏掉了跨境例外条款。

若候选提出实际修改订单的调用，隔离层必须阻止执行并记录，而不能让候选拥有生产写入权限。

6. 与易混淆概念的区别

离线评测用准备好的固定样本；影子测试可用授权复制的代表性流量，但候选答案不向用户生效；金丝雀发布让少部分真实用户收到候选答案；A/B 测试一般研究真实用户群体的效果差异，不一定有严格的安全阻断目标。

7. 实际工作中如何使用

优先从只读问答系统起步；保持输入请求关联 ID，记录两个版本的结论、来源引用、耗时、Token 与失败原因。控制或记录知识库版本、工具状态和时间差；如果两个版本读到不同的制度，就不能把差异全部归咎于模型。先通过离线闸门，再做合规影子验证。

8. 常见误区

  1. 影子测试绝对无风险：错误；数据复制仍有隐私、成本和系统负载风险。
  2. 不返回候选回答就不会影响生产：错误；副作用工具可能已经执行。
  3. 候选没有产生差异就一定正确：错误；两个版本可能一起犯错。
  4. 影子成功等于真实用户灰度必然成功：错误；用户行为与状态可能变化。

9. 思考题

如果影子 Agent 调用了真实“发短信”工具，但它的最终文字答案没有返回用户，这是否是安全的影子测试？应从权限、模拟工具和执行环境三个方面怎样改造？

LESSON 04/05真实小流量 / 渐进上线

Canary Deployment：金丝雀发布

英语主词条：Canary Deployment　IPA：/kəˈner.i dɪˈplɔɪ.mənt/　中文近似：肯耐瑞 · 迪普洛伊门特　含义：金丝雀发布／小流量灰度发布（发音播放器见页面顶部）

1. 一句话理解

金丝雀发布让一小部分真实用户或流量先使用新版本，在监控风险后再决定扩量、暂停或回滚。 与影子测试不同，这些用户真正会接收到新版本的结果。

2. 为什么需要它？解决什么问题？

测试环境无法完整复现生产中的并发、缓存、状态、连续会话、权限组合和真实用户输入。即使离线与影子测试通过，真实部署仍可能出错。逐步曝光新版本可以限制故障影响范围，但不能代替上线前安全评测。

3. 核心原理和工作机制

一种教学用阶段安排：离线闸门通过 → 影子测试通过 → 1% → 5% → 20% → 100%。这些百分比只是示例，不能照抄成所有业务的强制策略。每一阶段需要足够时长、样本量、可比流量和明确停止标准：关键安全违规立即停止；错误率或 P95 显著恶化则暂停分析；关键质量下降则回滚或保持稳定版。必须分开统计候选与对照组，避免总体平均数掩盖候选系统的问题。Google SRE 专门强调流量代表性、候选/对照组区分和观察窗口的选择。

4. 贴近日常或软件开发的类比

新菜单先在部分门店提供，而不是一次性替换所有门店。但试点客人真的会吃到新菜品，所以不能拿明显存在安全问题的菜品试点。AI 的灰度流量也是实际用户，不能把它当成无风险实验对象。

5. 一个真实 AI 场景示例

企业退款助手 V2 先开放给少量经过授权的内部员工。观察关键制度结论、人工纠正比例、P95、请求成本、工具异常和权限拒绝。假如 V1 业务错误率 0.5%、V2 候选组 4%，要核查是否为版本引起、样本和流量结构是否可比，并暂停扩量；不要把 V1 与 V2 合并统计后报告整体服务正常。数字为情境示例。

6. 与易混淆概念的区别

  • 影子测试：候选不影响用户答案；金丝雀：候选实际为部分用户服务。
  • 蓝绿部署：组织两套环境并切换或分流；它可以与金丝雀结合。
  • 功能开关：用于控制是否启用某项能力，但开关本身不等于质量判断。
  • A/B 实验：通常着眼业务或体验效果，质量门槛仍需单独定义。

7. 实际工作中如何使用

记录并可还原应用代码、模型标识、提示词版本、检索配置、工具版本、知识库快照、分流规则和回滚目标。进入真实灰度前完成必要的离线与影子验证；高风险写操作优先采用只读试点、人工审批或更严格的独立安全措施。每阶段按已定义指标做升流、保持或回退决策。

8. 常见误区

  1. 灰度流量越小就越有结论：错误；过少请求无法暴露少见故障。
  2. 没有投诉表示正常：错误；错误可能不会立即被发现。
  3. 只替换模型而没改代码便无需发布流程：错误；行为同样可能变化。
  4. 使用总体指标就足够：错误；必须区分候选和对照。

9. 思考题

候选仅处理了 20 个真实请求，全部成功。能否立即从 1% 升到 100%？你还需要怎样的样本量、时间窗口、分层流量和安全指标？

LESSON 05/05持续运行 / 止损恢复

上线后监控、漂移识别与回滚

1. 一句话理解

上线不是终点：必须持续观察业务正确性、安全、延迟和成本，识别输入或效果的变化，在必要时恢复已验证的状态或安排人工接管。

2. 为什么需要它？解决什么问题？

即使模型与代码不变，企业制度变更、RAG 索引落后、外部工具接口变化、用户问题分布改变、负载增加，也可能导致质量退化。昨日的评测通过不能无条件保证今天可靠。

3. 核心原理和工作机制

至少监控三类信号：

  • 运行健康：请求成功率、P95 延迟、超时率、工具错误、Token 与费用。
  • 结果质量：结论正确性、证据支持率、关键误判、转人工比例、人工纠正记录。
  • 输入分布：问题种类、文档版本、语言、长度、异常请求比例。

输入漂移指请求分布变化；质量退化指结果指标变差。两者可能有关，但不是同义词。利用请求关联 ID 追踪检索、模型与工具调用过程；生产日志需脱敏与权限控制。OpenTelemetry 的追踪、日志、指标与 GenAI 语义约定可为实践提供统一结构，但部分生成式 AI 约定仍在发展，接入时要核对版本。

4. 贴近日常或软件开发的类比

和微服务 SRE 类似：HTTP 返回 200 只能说明服务回答了，并不能证明业务结果正确。AI 系统也可能快速返回一段毫无证据的错误文字。类比的边界在于：AI 质量还需要评测集、人工标签或可信规则，不是传统 HTTP 指标就足够。

5. 一个真实 AI 场景示例

制度最近更新后，系统表现如下：HTTP 成功率 99.9%、延迟正常，跨境退款错误答案突然增加，引用仍指向旧制度。排查：①确认制度生效时间；②核查原文同步；③核查索引更新；④核查检索引用；⑤重新跑黄金评测集；⑥若新版本导致问题则按预案回滚；⑦若旧版也引用过时制度，就应修复知识数据或暂停高风险自动判断，不能盲目回滚。

6. 与易混淆概念的区别

  • 日志记录离散事件；追踪串联一个请求内的多个操作；指标展示聚合趋势。
  • 回滚恢复代码或配置，并不自动撤销已发生的外部写操作。
  • 业务补偿针对已发生的付款、发送邮件或订单修改等副作用，需要明确授权与审计。
  • 输入漂移不必然等于质量变差；质量退化也可能发生在输入稳定时。

7. 实际工作中如何使用

对每次请求保留非敏感关联 ID、应用版本、模型与提示词版本、检索索引版本、工具状态、错误类型、耗时与成本。必要时用经批准的脱敏样本进行人工回查。将确认的线上失败样例审核后纳入回归集，形成“失败 → 复核 → 评测更新 → 再发布”闭环。不得无限制记录原始用户问题、企业机密或 API 凭据。

8. 常见误区

  1. HTTP 全部成功就是业务质量可靠：错误。
  2. 原样记录所有模型输入输出最便于排错：可能侵犯隐私并泄露机密。
  3. 版本回滚自动修复所有损害：错误；外部操作可能已发生。
  4. 检测到漂移就必须立即换模型：错误；应先定位知识库、分布与业务变化来源。

9. 思考题

制度已经更新，旧版与新版 AI 都在引用过期条款：你会优先回滚模型，还是核查制度版本与索引同步，并设置人工兜底？说明原因和处理顺序。

PRACTICE纯离线 / Python 3

今日微型练习：离线 AI 发布闸门

目标：在无外网、无真实模型 API 的条件下，用一个模拟退款助手复现“新版本在高风险例外上出现回归，因此应该被发布闸门阻断”的现象。

环境与材料：Python 3、标准库、一个文本编辑器和八条虚构用例。适合 Windows PowerShell；不需要 GPU、数据库或服务凭证。

步骤 1：建立模拟规则和八条样本

将下面完整代码保存为 ai_release_gate.py。其中 stable() 模拟稳定版，candidate() 故意遗漏跨境例外。脚本不调用大模型，其目的是验证评测与发布逻辑。

CASES = [
    ("C01", "normal", 2000, "普通审批"),
    ("C02", "normal", 5000, "普通审批"),
    ("C03", "normal", 6000, "财务复核"),
    ("C04", "cross", 4800, "财务复核"),
    ("C05", "cross", 100, "财务复核"),
    ("C06", "normal", 0, "转人工"),
    ("C07", "normal", None, "转人工"),
    ("C08", "unknown", 3000, "转人工"),
]

def stable(order_type, amount):
    if order_type not in ("normal", "cross"):
        return "转人工"
    if amount is None or amount <= 0:
        return "转人工"
    if order_type == "cross" or amount > 5000:
        return "财务复核"
    return "普通审批"

def candidate(order_type, amount):
    # 故意遗漏跨境例外规则
    if order_type not in ("normal", "cross"):
        return "转人工"
    if amount is None or amount <= 0:
        return "转人工"
    return "财务复核" if amount > 5000 else "普通审批"

def evaluate(fn):
    correct = 0
    critical_errors = 0
    exception_ok = 0
    for case_id, kind, amount, expected in CASES:
        actual = fn(kind, amount)
        ok = actual == expected
        correct += int(ok)
        if kind == "cross":
            exception_ok += int(ok)
            critical_errors += int(not ok)
        print(case_id, "预期:", expected, "实际:", actual, "通过:", ok)
    accuracy = correct / len(CASES)
    exception_recall = exception_ok / 2
    gate = accuracy >= 0.95 and exception_recall == 1 and critical_errors == 0
    print("准确率:", f"{accuracy:.1%}")
    print("例外召回率:", f"{exception_recall:.1%}")
    print("关键错误:", critical_errors)
    print("发布闸门:", "PASS" if gate else "BLOCK")
    return gate

print("=== 稳定版本 ===")
evaluate(stable)
print("\n=== 候选版本 ===")
evaluate(candidate)

print("\n=== 本地影子对照差异 ===")
for case_id, kind, amount, expected in CASES:
    live = stable(kind, amount)
    shadow = candidate(kind, amount)
    if live != shadow:
        print("影子差异:", case_id, live, "!=", shadow)

步骤 2：运行，观察预期输出

在 PowerShell 中执行：

python .\ai_release_gate.py

预期旧版准确率 100.0%、例外召回率 100.0%、关键错误 0、闸门 PASS；候选准确率 75.0%、例外召回率 0.0%、关键错误 2、闸门 BLOCK。这些是教学函数的预期结果，不是实际模型成绩。

步骤 3：解释关键失败

候选版本只根据金额进行审批判断，遗漏 order_type == "cross"，因此 C04 和 C05 都错了。这说明关键例外应有独立质量阈值，不能被总体平均值稀释。

步骤 4：模拟影子对照

稳定版输出被当作用户实际看到的结果；候选版只用于对照。代码最后会列出 C04、C05 的差异。这里是本地影子比较模拟，没有复制任何生产请求，也没有触发副作用工具。真实影子测试需要授权、隔离和脱敏。

步骤 5：设计金丝雀策略

发布策略：离线闸门不通过则不进入影子或真实灰度；影子发现关键例外问题则禁止真实灰度；真正进入灰度后，应比较候选组与对照组，并定义最小样本、观察期、安全停止条件与回滚目标。本例候选被离线闸门阻断，不得进行真实金丝雀发布。

步骤 6：修复缺陷后再验收

将候选函数的最后一行修改为包含跨境特殊判断，让八条样本重新全对。再增加一个“缺失退款类型”样本，解释为什么应转人工。八条全部正确只说明通过现有模拟集，并不意味着真实生产安全。

故障与风险检查

如 python 不在 PATH，Windows 可以尝试 py .\ai_release_gate.py；不要把真实客户信息、令牌或内部财务制度复制进公开教学脚本。不能把模拟准确率当成真实大模型评测结果。
