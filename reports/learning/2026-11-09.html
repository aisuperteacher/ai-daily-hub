AI Coding Agent 工程系列 · 第 3 个进阶单元｜约 45 分钟

① Tool Schema：工具契约

1）一句话理解

工具契约是工具对外公布的机器可读取说明，规定工具名称、允许参数、类型、必填条件和返回约定。例如创建 Issue 的工具需要仓库、标题、正文；模型不能凭“创建一个 Issue”跳过参数结构。

2）为什么需要它／解决什么问题

自然语言的边界不严格。模型可能生成：

{"repo":"team/project","title":123,"body":"修复退款异常","auto_delete":true}

title 应为字符串却变成数字，还出现未定义的 auto_delete。直接执行模型输出可能导致失败或意外操作。Schema 是结构验证的第一层，不是授权系统。

3）核心原理和工作机制

处理顺序：注册工具并声明结构 → 模型生成工具调用参数 → 应用校验结构、权限和业务条件 → 真实执行并返回结果。在受支持的 OpenAI 函数调用配置中，strict: true 可让参数遵循所支持的 JSON Schema 子集；严格模式通常要求 additionalProperties: false 以及字段满足必填规则。参考 OpenAI Function Calling 官方文档。

一个简化参数 Schema：

{
  "type":"object",
  "properties":{
    "repository":{"type":"string"},
    "title":{"type":"string"},
    "body":{"type":"string"}
  },
  "required":["repository","title","body"],
  "additionalProperties":false
}

Schema 合法不代表业务合法。 例如仓库是字符串，不等于用户获准访问；标题的类型正确，也不等于标题的事实正确。还必须校验授权、范围、业务状态和危险副作用。模型提出动作不代表动作已执行成功。

4）贴近日常或软件开发的类比

类似 Java 方法签名：

Issue createIssue(String repository, String title, String body);

调用者必须提供符合类型的参数，但是方法签名本身不能确保仓库存在或调用者有权限。类比边界： LLM 工具调用还涉及模型生成、序列化与外部执行，不是 JVM 内部的普通同步方法调用。

5）一个真实 AI 场景示例

Coding Agent 从退款 Bug 描述中生成工具请求：

{
  "repository":"demo/refund-service",
  "title":"修复退款查询空值问题",
  "body":"复现条件：不存在的订单编号触发异常"
}

Harness 校验三个字段、检查仓库在许可范围内，然后向 GitHub API 发起请求。只有收到可确认的成功结果及 Issue 编号，才能把“已创建”作为事实；请求未执行时只能称“准备创建”。

6）与易混淆概念的区别

概念 区别
Tool Schema 定义调用数据结构
JSON Mode 使输出符合 JSON 格式，不必然符合业务 Schema
Structured Outputs 在支持的条件下约束结构符合性
MCP 工具和资源发现、调用与交换的协议
权限策略 决定用户和工具有没有权执行操作
业务校验 确认业务对象和状态是否合法

工具结构合法只是必要条件之一，不是业务安全的充分条件。

7）实际工作中如何使用

优先设计职责单一、参数明确的工具，而不是让万能 execute_command 处理所有操作。创建 Issue 可以强制提供业务编号，限制仓库许可范围，校验标题长度。工具执行后返回结构化、可确认的结果：

{"status":"created","issue_id":125,"url":"https://github.com/demo/refund-service/issues/125"}

该 URL 和编号仅是教学示例，未实际创建 Issue。

8）常见误区

  • JSON 能解析就代表调用正确？ 错。类型、范围与授权可能错误。
  • Strict Schema 能防止所有危险操作？ 错。它解决结构符合性，不解决业务权限。
  • 模型输出工具调用就等于操作执行？ 错。外部程序需要真正执行，可能被拒绝或失败。
  • 工具越通用越好？ 不一定。过宽权限会增加误操作风险。

9）思考题

模型生成完全符合 Schema 的请求，但仓库属于另一团队的私有项目。应在哪一层拒绝？为什么不能只在提示词中写“不要访问其他团队仓库”？

② Idempotency：幂等性

1）一句话理解

幂等性是同一业务操作重复执行多次，其最终业务效果与执行一次相同。 这里强调最终业务效果，不要求请求数、日志数或内部步骤相同。

2）为什么需要它／解决什么问题

Agent 请求创建 Issue。服务器已经创建成功，但返回响应途中网络断开，Agent 只收到 Request timed out。此时存在三种可能：请求没到达；到达但执行失败；已经创建成功只是响应丢失。模型无法从超时本身准确断定服务器是否已完成写入。直接重新创建可能导致两个 Issue。

3）核心原理和工作机制

为业务意图分配稳定标识：issue:create:T-1001。服务器在同一业务范围内查找该幂等键：若已成功，返回原结果；若正在执行，报告执行中或待核对；若不存在，竞争获取执行权并执行，最后原子记录结果。

收到创建请求
  ↓
检查相同业务操作键
  ├── 已成功 → 返回原 Issue ID
  ├── 执行中 → 返回待确认状态
  └── 不存在 → 原子取得执行权 → 操作 → 保存结果

检查与获取执行权必须并发安全。下面是不安全的伪代码：

if key not in database:
    create_issue()
    database.add(key)

两个并发请求都可能认为键不存在。需要唯一约束、事务、状态机以及下游 API 支持的幂等机制。若同一键对应不同参数，应拒绝；若外部系统不支持幂等，本地记录也不足以保证外部副作用绝不重复。写入超时应先查询状态。

4）贴近日常或软件开发的类比

用户连续三次点击“支付”，理想情况下同一笔业务不应扣款三次。系统通过订单号、交易号和支付服务支持的去重机制保护业务。类比边界： 不是所有创建、发邮件、部署和支付操作天然支持幂等，必须针对实际副作用设计。

5）一个真实 AI 场景示例

Agent 对工单 T-1001 发起：

create_issue(ticket_id="T-1001", idempotency_key="issue:create:T-1001")

首个请求超时。第二次保持同一个键。如果接收方可靠保存结果并提供查询，第二次应得到原 Issue ID，而不是新建。只在参数中加一个叫 idempotency_key 的字段，不意味着第三方服务支持了幂等。 必须核对其实际契约。

6）与易混淆概念的区别

概念 区别
幂等 避免重复业务副作用
去重 判断消息或请求是不是重复
重试 再次发起尝试
Exactly-once 端到端处理语义目标，不能只靠一个键保证
事务 协调数据操作的原子性等属性
补偿操作 出错后通过新业务动作修正影响

幂等和重试常一起使用，但任何一个都不能自动替代另一个。

7）实际工作中如何使用

写操作记录 business_operation_id（稳定业务意图）、request_fingerprint（防同一键混用不同请求）、execution_status（待执行／执行中／已成功／已失败／结果未知）。优先采用下游服务明确承诺的幂等能力；没有时增加状态查询、人工核对和补偿策略，不承诺绝对不重复。

8）常见误区

  • POST 天生不能幂等？ 应用可以为 POST 实现幂等语义。
  • 请求多带一个 UUID 就完成了？ 服务端必须持久化并约束它。
  • 重试应生成新幂等键？ 同一业务重试一般复用原键。
  • 本地数据库保存了记录，外部 Issue 一定不重复？ 两处持久化之间存在失败窗口。

9）思考题

创建 Issue 成功了，但 Agent 在保存 Issue ID 前崩溃。重启只看到“执行中”，怎样不盲目创建第二个 Issue？第三方 API 没有幂等功能时怎么办？

③ 失败分类与退避重试

1）一句话理解

可靠重试要先判断错误是否可以恢复，再在有界次数内、用合适的等待间隔重试，并考虑写操作可能产生的副作用。

2）为什么需要它／解决什么问题

常见结果包括 400 参数错误、401 凭据失效、403 禁止访问、404 资源不存在、429 限流、500 服务内部错误和网络超时。403 权限不足时无限重试没意义；429 可以按限制信息适当等待；创建操作超时却必须先确认副作用是否已发生。

3）核心原理和工作机制

错误类别 代表情况 典型处理
确定性失败 非法参数、权限拒绝 修正问题或停止
可恢复的临时故障 限流、短暂不可用 有界重试加退避
结果未知 写操作过程中请求超时 查询结果，不盲目再次执行

指数退避的一个简单公式为：d(n) = min(d_max, d_0 × 2^(n−1))。初始等待 1 秒、上限 8 秒时，前四次间隔是 1、2、4、8 秒。生产环境常加入随机抖动，避免客户端同时重试形成流量峰值。若服务端给出有效的 Retry-After，应按其规则处理。注意：退避只决定何时再试，不决定是否允许再试。

4）贴近日常或软件开发的类比

电话占线可以稍后再拨，号码错误必须改正；业务受理成功但通话中断则应先查受理状态，不能重新提交。类比边界： API 的可重试性应依据实际协议和下游文档，而不是电话类比决定。

5）一个真实 AI 场景示例

GitHub Issue 创建接口返回 422：检查提交参数，不要原样重试。返回 429：依据速率限制等待；写入超时：以工单业务标识查询是否已有 Issue。工具层应尽可能返回机器可识别的状态：

{
  "status":"outcome_unknown",
  "retryable":false,
  "reason":"write_timeout_result_unknown",
  "operation_id":"issue:create:T-1001"
}

此处 retryable:false 表示不能直接盲重试，不是永远不能恢复；核对实际状态后可选择受控恢复。

6）与易混淆概念的区别

概念 作用
重试 再次尝试同一操作
退避 控制两次尝试的等待间隔
超时 等待超过期限，不证明服务器一定失败
断路器 故障持续时暂时阻断请求
幂等 保护重复操作不产生重复副作用
人工介入 无法安全决定时交给授权人员

7）实际工作中如何使用

把工具结果归类为 success、permanent_failure、transient_failure、outcome_unknown，为每类确定不同处理。设置最大尝试次数、总耗时预算、单次超时、限流策略和未知结果查询路径。禁止无限重试；多个 Agent 同时处理一笔业务时要特别注意并发重复。

8）常见误区

  • 所有 5xx 都要立即无限重试？ 错，可能放大故障。
  • 超时就是没执行？ 错，响应可能丢失。
  • 增加重试次数必定提升成功率？ 错，过量重试可能使下游更不稳定。
  • 让模型自由判断错误即可？ 不够，工具层需提供明确状态。

9）思考题

一个只读工具连续三次返回 429，另一个创建 Issue 的写操作发生网络超时。为什么两者不能采用同一套自动重试方案？

④ Checkpointing：检查点持久化与恢复

1）一句话理解

检查点将任务执行进度、已经确认的结果和未完成的操作保存为可恢复的持久状态。 目的是在长任务中断后继续，而不是重新乱做一遍。

2）为什么需要它／解决什么问题

一个 Agent 流程为：读取工单 → 查询重复 Issue → 创建 Issue → 更新工单状态 → 生成报告。若第三步后进程突然终止，从第一步重做可能重复创建；直接跳到最后又可能漏掉工单更新。检查点解决执行连续性和确定恢复入口的问题。

3）核心原理和工作机制

一种检查点结构：

{
  "workflow_id":"ticket:T-1001",
  "phase":"create_issue",
  "status":"outcome_unknown",
  "operation_id":"issue:create:T-1001",
  "issue_id":null,
  "version":3
}

恢复时要核对任务身份、记录完整性、状态是否过期、外部操作是否产生结果和下一动作的重复风险。合理的状态机为：待执行 → 已取得执行权 → 发起外部调用 → 已确认成功／已确认失败／结果未知；成功要保存结果再推进，未知结果先查询或人工处理。

难点：检查点保存和外部 API 的副作用往往不在同一个原子事务中。 即使外部已成功，本地保存失败仍可能发生，因此要配合幂等、状态查询和必要的补偿操作。

4）贴近日常或软件开发的类比

游戏保存进度，重启可以从某关继续。但真实 Agent 可能已经发邮件、建 Issue 或更新数据库，这些外部动作不会随本地存档自动回滚。检查点是记录状态，不是时间倒流。

5）一个真实 AI 场景示例

Agent 为三个工单创建 Issue，前两个已完成、第三个中断：

T-1001 → Issue 125 → 已确认
T-1002 → Issue 126 → 已确认
T-1003 → 结果未知

恢复时保留前两个已确认记录，不再次创建；对第三个先检查远端是否已有对应 Issue，再决定继续还是人工处理。然后生成准确的汇总报告。

6）与易混淆概念的区别

概念 区别
检查点 保存任务执行状态供恢复
上下文压缩 浓缩模型下一轮看到的会话内容
Git Commit 保存代码文件版本
数据库事务 管理特定范围的数据原子性
任务日志 记录已经发生的事件
事件溯源 用事件记录重建状态的设计模式

检查点回答“从哪里安全继续”，上下文压缩回答“模型应该看到哪些关键信息”。

7）实际工作中如何使用

重要有副作用流程至少保存 workflow_id、business_operation_id、current_phase、execution_status、external_result_id、last_updated_at、state_version，使用持久化存储。并发恢复时通过版本号、租约或互斥机制防止两个执行器同时恢复同一任务。短小只读任务一般无需引入复杂检查点设施。

8）常见误区

  • 最后一条聊天消息就是检查点？ 通常不是严格业务状态。
  • 有检查点就不需要幂等？ 外部执行和本地保存间有故障窗口。
  • 重启后直接去下一步骤？ 必须核对结果未知操作。
  • 需要每个 Token 都持久化一次？ 不必，应根据业务阶段与恢复成本选择。

9）思考题

如果创建 Issue 成功但本地检查点写入失败，为什么把检查点提前写入也无法彻底解决？应该如何定义操作的恢复语义？

⑤ 执行轨迹与故障注入评测

1）一句话理解

执行轨迹保存 Agent 从输入到结果的重要工具动作和状态，故障注入主动制造异常，检查系统是否能够保持正确的业务结果。 结合两者才能超越“理想环境演示成功”。

2）为什么需要它／解决什么问题

正常网络下运行十次都成功，不代表遇到 API 响应丢失、请求超时、参数异常、进程终止、外部成功但本地保存失败、多个 Agent 并发同一工单时仍可靠。测试必须覆盖失败、并发与恢复路径。

3）核心原理和工作机制

重要轨迹字段：任务编号、工具调用编号、工具名称、关键参数摘要、开始时间、状态、外部结果 ID、重试次数、最终状态。示例：

Task: T-1001
  ├─ validate_input → success
  ├─ lookup_issue → not_found
  ├─ create_issue → timeout / outcome_unknown
  ├─ lookup_issue → found / 125
  └─ finalize → success

这个轨迹说明系统没有因一次超时就盲目再次创建。故障注入的期望行为：缺参数时不调用下游；创建成功但响应丢失时查询状态；429 时限流等待；403 时停止；进程中断时恢复并核对；并发重复请求不产生重复业务副作用。注意日志需要脱敏和最小化，不应记录密钥与不必要的个人数据。

4）贴近日常或软件开发的类比

分布式系统用日志、链路追踪和故障演练检验服务可靠性；订单系统即使返回 200，也需要确认实际支付是否重复或遗漏。Agent 还需要额外检查模型选择的动作是否正确、是否满足停止条件。类比边界： 工具调用成功不证明模型决策正确。

5）一个真实 AI 场景示例

流程 A 在创建请求超时后直接重试三次；流程 B 先按业务标识核对远端状态，确认没有完成才继续。注入“创建成功但响应丢失”故障时，A 可能创建重复 Issue，B 在远端状态可可靠关联的条件下能避免重复。这是教学推演，不是任何具体产品的实测结论。

今日串联：从工具调用到可靠完成任务

逻辑知识链：工具契约 → 幂等性 → 失败分类与退避 → 检查点持久化 → 执行轨迹与故障注入评测。 它不是严格的串行执行链；授权、日志、状态记录和错误处理可贯穿整个流程。

对于“为工单 T-1001 创建 Issue，再把工单状态改为已处理”的任务，合理流程是：接收工单 → 校验结构及权限 → 查重 → 分配稳定操作标识 → 发起创建 → 成功则记录 Issue ID，失败则按类型处理，结果未知则查询或人工核对 → 确认已创建 → 更新工单状态 → 验证两边实际结果 → 保存轨迹并报告确认事实和风险。

可靠 Agent 的关键不是每次都成功，而是失败时也不会随意破坏业务状态。

第二步：输入并运行完整代码

class LostResponse(Exception):
    pass

class FakeIssueService:
    def __init__(self):
        self.issues = {}
        self.next_id = 100
        self.lost_once = set()

    def create(self, key, payload):
        fingerprint = (payload["ticket_id"], payload["title"])
        if key in self.issues:
            saved_fingerprint, issue_id = self.issues[key]
            if fingerprint != saved_fingerprint:
                raise ValueError("同一幂等键对应不同请求")
            return issue_id

        issue_id = self.next_id
        self.next_id += 1
        self.issues[key] = (fingerprint, issue_id)
        if key not in self.lost_once:
            self.lost_once.add(key)
            raise LostResponse("Issue 已创建，但响应丢失")
        return issue_id

service = FakeIssueService()
payload = {"ticket_id":"T-1001", "title":"修复退款查询异常"}
key = "issue:create:T-1001"
try:
    result = service.create(key, payload)
except LostResponse as exc:
    print("第一次调用：", exc)
    result = service.create(key, payload)
print("最终 Issue ID：", result)
print("实际 Issue 数量：", len(service.issues))

第三步：核对预期结果

预期：

第一次调用： Issue 已创建，但响应丢失
最终 Issue ID： 100
实际 Issue 数量： 1

为什么只有一条？第一调用保存了业务操作键和结果，第二次用同一键找到了历史结果。这是单进程内存模型，不能保证真实 GitHub API 幂等、并发安全或崩溃恢复。

设计四种模拟结果：invalid_argument、permission_denied、rate_limited、response_lost。期望策略依次是修正参数、报告权限、有限等待重试、查询执行状态。不要用一个统一的 except Exception: retry() 处理所有问题。
