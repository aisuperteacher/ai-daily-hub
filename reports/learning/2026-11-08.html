今日主题：高级 RAG 工程——为什么知识库里明明有答案，AI 却找错、答错甚至编造依据？

今天从之前学过的 RAG、Embedding 和模型评测继续向前推进。重点学习企业级 RAG 上线时的五个关键环节：检索漏召回、排序质量、用户问题理解、回答是否有证据、以及分层定位故障。

贯穿全课的业务案例：企业制度规定“普通退款在 5000 元以下不需要财务复核”，但同时规定“跨境退款无论金额多少均需要财务复核”。用户问：“4800 元跨境退款需要财务复核吗？”正确答案是“需要，因为跨境退款的特殊规定适用”。如果系统只找到普通规则，就容易错误回答“不需要”。

知识点① Hybrid Search：混合检索

1. 一句话理解

混合检索把关键词检索与向量语义检索的候选结果合并，让系统既能精确匹配编号、专业术语，也能识别不同措辞背后的相同含义。 它发生在检索阶段，并不是让大模型把同一个问题回答两次。

2. 为什么需要它／解决什么问题

关键词检索很擅长处理错误码 ERR-504、交易号 TX-2048、API 版本 V3.2 等精确字符。例如文档包含“ERR-504 是退款接口 V3.2 的超时错误”，搜索时就可以高精度匹配。

但是用户可能说“退款一直转圈，过很久才失败”，手册却写着“退款查询服务发生请求超时”。两个表达关键词重合度有限，但意思接近；向量检索有机会通过 Embedding 表达发现语义相似性。

向量检索也有缺点：对于专业缩写、订单编号、金额、版本号，近似语义不一定足够精确。因此，混合检索试图合并两种互补信号。

3. 核心原理和工作机制

系统将用户查询并行送入两个检索器。关键词检索（如 BM25）输出一组带名次的结果；向量检索按嵌入向量相似度输出另一组结果。随后使用某种融合算法，合并成统一候选列表。

用户问题
  ├─ 关键词检索 ── 候选列表 A
  └─ 向量检索 ──── 候选列表 B
                      │
                 排名融合
                      │
                   统一列表

不要直接把关键词分数 8.7 与向量相似度 0.82 相加：两者来自不同算法，量纲和分布通常不同。

常见的 RRF（倒数排名融合） 使用名次而不是原始分数：

RRF(文档) = Σ [1 / (k + 该文档在某列表中的名次)]

这里名次从 1 开始；未出现在某个列表时，该列表贡献 0；k 是平滑常数，教学例子使用 60。它与向量近邻数 top_k 是不同参数。Microsoft Azure AI Search 官方文档介绍了这套融合思路。

例如关键词结果是 A, B, C，向量结果是 B, D, A：

A = 1/61 + 1/63 ≈ 0.03227
B = 1/62 + 1/61 ≈ 0.03252
C = 1/63        ≈ 0.01587
D = 1/62        ≈ 0.01613

最终融合结果是 B, A, D, C。然而，排名融合不会决定“哪条业务制度优先适用”，业务规则仍需后续验证。

4. 贴近日常或软件开发的类比

你要排查一个 GitHub 项目的异常。一条路径是搜索完整的 NullPointerException 错误文字；另一条路径是搜索“对象为空导致请求失败”的自然语言描述。前者精确，后者补充同义表达。合并结果可以减少遗漏。类比边界：搜索得到的结果仍可能过期、错误或无权限访问。

5. 一个真实 AI 场景示例

金融知识库收到用户提问：“交易号 TX-2048 的跨境退款遵守什么审批规则？”关键词通道查找交易编号、跨境、审批等精确词项；向量通道查找海外结算退款审核要求等相近表达；合并后得到交易记录和制度候选，再核查是否属于当前有效版本。混合检索改善发现能力，但不自行授权读取交易隐私数据。

6. 与易混淆概念的区别

概念 职责
关键词检索 根据词项和字段的文本匹配发现文档
向量检索 根据语义向量和近邻相似度发现文档
混合检索 合并上述多种检索结果
重排序 对已经找到的候选做更精细的排序
RAG 将检索信息用于支持生成回答的整体架构

混合检索是 RAG 的可选组成部分，不是所有任务都必须启用。

7. 实际工作中如何使用

先分别建立关键词检索与向量检索基线，再使用同一批真实问题检验混合方案。尤其要覆盖 精确项测试（订单号、错误码、版本）、语义测试（口语、近义词）、权限测试（仅返回有权访问的资料）和 版本测试（当前规定与历史规定分开）。不要在权限过滤后置时依赖模型自动保密。Azure 和 Cloudflare 官方文档均介绍了关键词与向量混合的工作方式。

8. 常见误区

误区一：混合检索一定优于单一路径。 不一定；低成本、结构清晰的任务用单路检索可能更合适。

误区二：原始关键词分数与向量分数可以直接相加。 不严谨；量纲和数值范围未必相同。

误区三：排第一就等于业务上正确。 不对；相关性不等于真实性、生效性或业务优先级。

误区四：混合检索可以代替权限过滤。 不对；授权是可信数据访问边界的问题。

9. 思考题

用户精确查询 ERR-504，向量检索给出大量“请求失败”泛化文档，而关键词检索定位到了唯一的错误码说明。你会如何调整检索权重、精确过滤或结果校验？为何不能无条件让向量结果排第一？

知识点② Reranking：重排序

1. 一句话理解

重排序是在已经得到一批候选文档后，使用更细致的相关性判断方法重新排列它们。 首轮检索负责尽量找回可能相关的资料；重排序负责把对当前问题真正有用的候选尽可能靠前放置。

2. 为什么需要它／解决什么问题

用户问“4800 元跨境退款是否需要财务复核”，初次检索可能返回：第 1 名普通退款审批规则、第 2 名退款账户登记流程、第 3 名跨境退款特殊审批规则。第 1 名虽然关键词相关，却不能单独解决涉及例外条件的问题。若模型只读取前两条，便会丢失核心证据。

3. 核心原理和工作机制

常见重排序实现之一是交叉编码器。与预先为文档编码向量不同，它将查询与每个候选文本联合输入模型，对每对内容计算更细致的相关性评分：

[问题] + [普通退款规则]  → 评分1
[问题] + [跨境退款规则]  → 评分2
[问题] + [退款登记流程]  → 评分3
                            ↓
                       根据分数重排

相对初筛，联合评估通常更耗时、更耗计算。Azure AI Search 语义重排序可以在初始 BM25 或 RRF 排名后操作，当前其官方文档规定最多处理 50 个候选结果。这是该产品的机制限制，不是所有重排序器的共同限制。

最重要的边界：重排序无法补充第一阶段完全没有召回的文档。 如果候选只有普通退款、账户登记和退款通知，没有跨境例外条款，再强的重排序器也不能把不存在的第四份文档重新排出来。

4. 贴近日常或软件开发的类比

你在代码仓库搜索 getRefund 找到三十个结果。第一次搜索是粗筛；接着阅读方法签名、调用链和测试，判断哪个方法与当前 Bug 更相关，便是细筛。若初次搜索完全漏掉目标模块，再精细筛选已有结果也无法找到它。

5. 一个真实 AI 场景示例

企业知识库初筛得到 30 条文档，包括普通退款阈值、跨境例外、客服登记说明和多个版本的制度。重排序使“跨境退款是否必须财务复核”的条款进入最终前 5。后续仍要判断文档生效日期、访问权限和规则冲突；重排序高分不是业务权威等级。

6. 与易混淆概念的区别

概念 作用
召回 找到可能相关的资料
重排序 更精确地安排已有候选的名次
生成模型 根据问题和证据组织回答
业务规则引擎 严格执行确定性的业务条件
版本治理 判断哪份资料当前有效

重排序分数描述相关性，不是已经校准的答案正确概率。

7. 实际工作中如何使用

以混合检索为基线，先试验例如 20—50 条候选，再对比是否增加重排序。记录正确证据进入最终 Top 5 的比例、P95 延迟和单次请求成本。如果正确证据长期不出现在候选中，应先优化检索、分块和查询，而不是单纯购买更强的重排序模型。

8. 常见误区

误区一：重排序能解决所有漏召回。 不对，它不能排列没有被找出的证据。

误区二：重排序分数等于答案正确率。 不对，它通常是相关性评分。

误区三：候选越多就越好。 不一定，候选增加可能带来延迟和费用。

误区四：最相关的旧制度可以覆盖新制度。 不对，版本和法律业务优先级独立于文本相关性。

9. 思考题

正确的跨境退款条款从未出现在初筛 Top 50 中，团队计划换更贵的重排序模型。你会同意吗？为什么？应首先检查哪几类召回问题？

知识点③ 查询改写与问题分解

1. 一句话理解

查询改写把用户口语、含混表达转成更适合检索的表达；问题分解把一个复杂问题拆成若干必须分别查证的子问题。 两者一般发生在检索前或检索规划阶段。

2. 为什么需要它／解决什么问题

真实用户不一定使用文档里的正式术语。例如：“那个国外订单，钱没回来，按照新规是不是得找财务？”这里至少有三个歧义：“国外订单”是不是跨境交易、“钱没回来”是退款申请还是清算延迟、“新规”指哪个有效制度。如果直接全文检索，可能得到大量不相关结果。

3. 核心原理和工作机制

查询改写保持用户意图，生成一条或几条更便于检索的表达：

原话：国外订单退款为什么一直不到账？
改写候选：跨境退款到账时间
          跨境退款清算延迟
          退款失败与资金退回流程

问题分解则辨认独立证据需求。对于“4800 元跨境退款按照当前制度是否需要复核”，可拆成：

子问题 A：当前普通退款的金额审批规则是什么？
子问题 B：跨境退款的当前特殊规则是什么？
子问题 C：普通规则与特殊规则冲突时哪个优先？

改写或分解形成的是检索计划，不是事实声明。 如果“客户在国外”不等于“跨境交易”，就不能替用户直接补成“已确认跨境交易”。改写必须保留原始问题与不确定条件，便于追踪。

4. 贴近日常或软件开发的类比

线上用户说“系统好像慢了”，工程师往往分成 HTTP 超时、数据库慢查询、下游服务异常、最近部署变更等调查方向。把抽象描述改成可搜索的问题能加速定位，但每一种方向都是待验证的假设，而不是确定的故障原因。

5. 一个真实 AI 场景示例

用户说“退款不到五千，客户在国外，是不是不用审核？”可以先形成这样的检索计划：

{
  "original_question": "退款不到五千，客户在国外，是不是不用审核？",
  "uncertain_terms": ["客户在国外是否等于跨境交易"],
  "queries": [
    "普通退款5000元以下审批要求",
    "跨境退款财务复核制度",
    "跨境交易判定标准"
  ]
}

这只是教学数据格式。若业务数据不能确认该交易属于跨境，最终回答应保留条件和不确定性，不得擅自下判断。

6. 与易混淆概念的区别

概念 核心区别
查询改写 保留意图并优化检索表达
问题分解 将复杂任务拆为多项证据需求
重排序 调整已有候选的排列顺序
意图识别 判断用户希望完成的业务任务
提示词优化 调整模型接受的指令及上下文组织

查询改写不是把提示词写长，而是为了实际改进证据召回。

7. 实际工作中如何使用

保留原始问题、改写内容和检索结果。重点在口语、同义词、多条件和跨文档推理时使用多查询；对简单精确编号查询（如 TX-2048）则应谨慎，过度改写可能破坏精确 ID。对可能涉及身份、权限、金额和法律含义的歧义，优先查询可信业务系统或明确标注未知。

8. 常见误区

误区一：查询越长越好。 不一定，额外文字可能引入噪声。

误区二：自动改写能消除所有歧义。 不对，真实事实缺失需要核实或询问。

误区三：每个问题必须拆成十条查询。 不对，增加查询会产生延迟和成本。

误区四：模型改写时补出的内容等于真实事实。 不对，假设仍需证据。

9. 思考题

用户只说“帮我看看昨天那个海外退款是否需要审核”。没有订单编号，也不清楚“海外”表示客户所在地还是交易性质。你会直接改写、尝试已授权业务查询，还是先确认信息？应该根据哪些边界来决定？

知识点④ Groundedness：证据支撑性

1. 一句话理解

证据支撑性检查模型回答中的每一个事实性主张，是否确实由本次提供的可信证据支撑。 回答说得合理或附带链接，不等于每个主张都有可靠依据。

2. 为什么需要它／解决什么问题

模型获得文档“跨境退款无论金额多少都必须财务复核”，却回答：“必须财务复核，并且要在两个工作日内审批结束。”这包含两个不同主张：一是“必须财务复核”，有证据；二是“两个工作日”，当前证据没有。即使第二个主张在其他来源中偶尔正确，也不能依据当前证据声称已被证明。

3. 核心原理和工作机制

将回答分解成可独立核查的原子主张，再逐条与证据关联：

模型回答
  ├─ 主张 A：跨境退款必须财务复核 → 已支持
  ├─ 主张 B：审批必须两天完成 → 证据不足
  └─ 主张 C：当前版本适用此规则 → 需验证生效期

可以用一个教学指标表达支持情况：

支持率 = 有证据支持的事实性主张数 / 全部待验证事实性主张数

五项事实主张有四项得到支持，教学指标为 4/5=80%。这是解释性简化指标，不是各平台统一标准。

更深入的区别：有据不一定真实，有据也不一定有效。 旧制度可能充分支持“2024 年曾采用此规则”的陈述，但并不代表它仍适用于 2026 年的当前交易。若来源本身错误，引用它也无法保证现实正确性。

OpenAI 开源的知识检索示例在其评测数据中使用 citation_text 保存支持材料，体现了将证据与评测联系起来的思路。

4. 贴近日常或软件开发的类比

代码审查中有人说“接口延迟降低 50%”，必须提供可复现压测条件和数据；不能只有一张看起来不错的截图。RAG 同理，需要具体证据支持每一条业务结论。类比边界：业务证据还可能来自经过授权的结构化查询、交易系统或规则数据库，并不只限于网页文本。

5. 一个真实 AI 场景示例

可靠的回答可以带上证据 ID：

{
  "answer": "需要财务复核",
  "claims": [
    {
      "text": "跨境退款无论金额多少都需要财务复核",
      "evidence_id": "POLICY-CROSSBORDER-V3-08"
    }
  ],
  "unverified": []
}

这是教学格式。如果还没有足够数据确认“客户在国外”等于“交易为跨境退款”，应明确回答：“如果交易满足跨境退款定义，则需要财务复核；目前材料不足以确认交易分类。”

6. 与易混淆概念的区别

概念 核心问题
证据支撑性 回答由给定证据支持吗？
事实正确性 回答在现实世界中真实吗？
引用完整性 需要依据的结论附上了来源吗？
检索召回率 必需证据是否被找出？
业务合规性 回答或操作符合当前有效规则吗？

这几项有关联，但不是同义词。

7. 实际工作中如何使用

让检索结果携带文档 ID、版本、生效日期、条款位置和访问权限信息；要求模型为关键结论指定证据。高风险决策应独立检查引用是否支持结论、是否存在冲突条款、规则是否当前有效、用户是否拥有访问权限。资金审批、账户权限变更等最终操作仍由可信业务系统控制。

8. 常见误区

误区一：回答有引用就说明可信。 不对，引用可能与主张无关。

误区二：证据支持就代表当前事实正确。 不对，来源可能过期或错误。

误区三：模型写“根据规定”就代表真正查到规定。 不对，必须核查原始来源。

误区四：缺乏证据也要给完整确定答案。 不对，风险业务应明确不确定性。

9. 思考题

模型引用一份 2024 年旧制度，回答完全符合旧制度，但 2026 年的新制度与之冲突。证据支撑性、当前事实正确性和业务合规性分别如何评价？为什么需要分开判断？

知识点⑤ RAG 分层评测与故障定位

1. 一句话理解

RAG 分层评测将一次问答拆为查询理解、召回、排序、证据使用和业务结论等环节，分别测量并找出失败原因。 它回答“为什么错、该修哪里”，而不是只判断最终回复是否正确。

2. 为什么需要它／解决什么问题

RAG 答错，最直观但未必正确的反应是“换更强的大模型”。如果检索阶段根本没有找到跨境退款例外条款，生成模型缺少必要资料，单纯换模型不能保证修复；如果证据已进入最终上下文却被忽视，则更可能与提示组织、冲突处理或生成推理有关。

3. 核心原理和工作机制

建议设置五个评测关口：

用户输入 → ① 查询理解：改写是否偏离原意？
         → ② 检索召回：必要证据是否进入候选集？
         → ③ 排序质量：证据是否进入最终上下文？
         → ④ 证据使用：模型回答是否真正有据？
         → ⑤ 业务结果：是否符合当前有效规则？

检索常用指标之一是 Recall@K：

Recall@K = 前 K 个结果中找到的相关证据数量 / 全部应找到的相关证据数量

例如一道问题有两条必须找到的证据，Top 5 只找到一条，则 Recall@5=1/2=50%。如果仅关心至少命中一个关键证据，应该另设“关键证据命中率”，不可混用定义。

排序可以记录第一条正确证据的名次，以及 Top 3/Top 5 对必要证据的覆盖。生成层检查最终答案正确性、证据支撑性、遗漏条件和无依据主张；性能层记录 P95 延迟、Token 成本、检索费用和模型费用。

4. 贴近日常或软件开发的类比

微服务请求失败时，看到 HTTP 500 不能直接认定数据库坏了；需要从网关、服务、数据库到下游 API 逐层排查。RAG 类似：查询、检索、排序、证据、生成都可能造成最终失败。类比边界：RAG 涉及语义与业务有效性，无法把所有质量问题都量化为确定的网络错误码。

5. 一个真实 AI 场景示例

假设对 100 个经人工核对的退款问答样本进行三组测试：

方案 假设答案正确率 假设 P95 延迟
A：仅向量检索 76% 900ms
B：混合检索 84% 1100ms
C：混合检索＋重排序 88% 1600ms

以上全部为教学假设数字，未进行真实线上压测。 方案 C 比 B 多 4 个百分点，但 P95 增加 500ms。是否采用 C，应根据高风险错误的代价、额外成本和目标用户的响应体验判断。不能只看单一准确率。

6. 与易混淆概念的区别

概念 测量对象
Recall@K 必要证据的召回覆盖程度
排序指标 正确证据在结果中的先后位置
证据支撑性 事实性回答是否有依据
答案正确率 最终答案是否正确
任务成功率 业务目标是否真正完成
线上监控 部署后质量、延迟、成本是否变化

正确答案可能缺少引用；引用充分也可能使用过期制度，不能用一个分数替代全部判断。

7. 实际工作中如何使用

先建立小而可靠的人工校对测试集，至少包括问题、必需证据 ID、预期答案、预期推理依据、数据集版本。例如：

{
  "question": "4800元跨境退款是否需要财务复核？",
  "required_evidence": ["POLICY-CROSSBORDER-V3-08"],
  "expected_answer": "需要",
  "expected_reason": "跨境退款规则优先适用",
  "dataset_version": "rag-eval-001"
}

同时记录原始问题、查询改写、检索候选、融合排名、重排序、最终证据、生成回答、实际耗时。若正确证据未出现，先查索引/召回；若出现但进不了上下文，查排序和截断；若已进入仍被忽视，查提示及推理；若引用了旧制度，查版本治理。

8. 常见误区

误区一：最终准确率低一定要换模型。 不对，原因可能是数据、索引或检索。

误区二：只评估最终回答，不评估检索。 这样无法明确定位优化方向。

误区三：评测样本越多就无需人工审核。 不对，错误标签会让评测失去意义。

误区四：一次离线提升就保证生产提升。 不对，还需考虑真实分布、权限、回归和性能。

9. 思考题

若 Recall@10 达到 98%，但最终答案正确率只有 72%，你应该先继续增加 Top K，还是检查证据排序、冲突制度、上下文构建和生成阶段？解释理由。

今日串联：五个知识点形成的完整知识链

今天五项能力贯穿同一条 RAG 工作流：

用户提出问题
    ↓
③ 查询改写与问题分解：明确需要哪些证据
    ↓
① 混合检索：关键词＋语义共同发现候选
    ↓
② 重排序：使必要证据优先进入模型上下文
    ↓
模型根据证据组织回答
    ↓
④ 证据支撑性：逐条检查事实主张
    ↓
⑤ 分层评测：判断失败发生在哪一层

图中是概念性处理顺序，不代表所有系统必须用完全相同的架构。权限过滤、当前制度版本与业务规则校验，应贯穿适当环节，而不是只在最后用一句提示词补救。

本期最重要的工程方法：先检查证据是否找到，再检查证据是否进入最终上下文，然后检查模型是否正确利用证据。 不要把所有 RAG 问题都归咎于大模型。

今日微型练习：30—45 分钟搭建可解释的排名融合实验

目标、输入与准备

目标：不调用付费 API、不安装向量数据库，使用 Python 标准库模拟两路检索结果的 RRF 融合，理解召回边界，并识别回答中的无依据主张。

输入的四条模拟文档：

A：普通退款在 5000 元以下不需要财务复核。
B：跨境退款不论金额多少，均需要财务复核。
C：退款申请需要登记客户账户信息。
D：国际结算可能受到清算时间影响。

提问：“4800 元跨境退款需要财务复核吗？”期望证据 B，正确回答：需要。

步骤一：建立 Python 文件

将以下代码保存为 rag_rrf_lab.py（代码使用 Python 3 标准库，无需额外依赖）：

KEYWORD_RESULTS = ["A", "B", "C"]
VECTOR_RESULTS = ["B", "D", "A"]

DOCS = {
    "A": "普通退款在5000元以下不需要财务复核",
    "B": "跨境退款不论金额多少均需要财务复核",
    "C": "退款申请需要登记客户账户信息",
    "D": "国际结算可能受到清算时间影响"
}


def rrf_fusion(result_lists, constant=60):
    scores = {}
    for results in result_lists:
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] = (
                scores.get(doc_id, 0.0)
                + 1.0 / (constant + rank)
            )
    return sorted(
        scores.items(),
        key=lambda item: (-item[1], item[0])
    )


ranked = rrf_fusion([
    KEYWORD_RESULTS,
    VECTOR_RESULTS
])

for doc_id, score in ranked:
    print(f"{doc_id}: {score:.6f} | {DOCS[doc_id]}")

在 Windows PowerShell 里运行 python rag_rrf_lab.py。

步骤二：观察预期输出

B: 0.032522 | 跨境退款不论金额多少均需要财务复核
A: 0.032266 | 普通退款在5000元以下不需要财务复核
D: 0.016129 | 国际结算可能受到清算时间影响
C: 0.015873 | 退款申请需要登记客户账户信息

B 同时位于关键词第二、向量第一；A 位于关键词第一、向量第三，因此 B 在 RRF 融合后略微领先。运行的是融合算法，不是真正计算 Embedding。

步骤三：修改条件进行反例测试

首先把 VECTOR_RESULTS 改为 ['D','C','A']，观察 B 排名变化。随后将两个列表都删除 B：

KEYWORD_RESULTS = ["A", "C"]
VECTOR_RESULTS = ["D", "A"]

重新执行后，B 不会被算法凭空生成。这证明：召回漏掉正确证据时，融合无法自动创造证据。

步骤四：进行证据核查

模型若说“跨境退款必须财务复核，且两天内完成审批”，应拆分成两条主张：第一条由 B 支持；第二条四份文档都未提供依据，标为“证据不足”。不能因为一句话前半段正确，就把后半段也视为已证实。

步骤五：定义故障与风险检查

运行遇到 SyntaxError，检查文件是否完整复制及缩进。结果顺序异常，核对两路列表、排名是否从 1 开始以及 constant 是否为 60。结果第一名与预期不同，不要直接修改答案，应先检查输入列表。真实业务接入前，还要单独实现权限、制度版本、生效时间和业务规则校验。

步骤六：验收标准

验收项目 达标要求
环境 只使用 Python 3 标准库
RRF 计算 按每个列表中的名次累计倒数分数
正常场景 B 排名第一
失败场景 两路都缺少 B 时，融合无法找回 B
证据判断 能区分被资料支持与证据不足的主张
概念理解 能解释混合检索、重排序、业务规则验证的区别

今日综合思考题

  1. 首轮检索没有正确制度，换更贵的重排序模型能直接找回吗？为什么？
  2. 回答附了相关制度网址，为什么仍可能缺少足够证据？
  3. Recall@10 已经很高，答案正确率仍低，应该优先检查哪些阶段？

今日学习结论

检索到相关资料，不等于找全必要证据；资料排在前面，不等于其当前有效；模型输出答案，不等于结论具有充分依据。 把这些区别落实为数据结构、运行轨迹、人工审核样本和分层评测，才能把 RAG 从演示原型提升为可持续治理的企业 AI 能力。
