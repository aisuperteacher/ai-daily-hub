二、OpenCode V1 1.19.6：V1 到 V2 正式升级入口

发布日期： 2026-11-17 07:21 UTC / 北京时间 15:21。

官方：GitHub V1 1.19.6 Release · 产品 Changelog。

2.1 V1 客户端主动提供 V2 升级选项

变化内容： OpenCode V1 客户端提供升级 OpenCode 2.0 的交互入口。V2 可在后台预下载，但只在用户选择 Restart to upgrade、Upgrade on quit 或 Later 后决定何时升级。官方称 Sessions、Projects 和 Settings 会保留，并明确表示 V1 Plugins 需要更新以适配 V2。

技术意义： 数据迁移和运行时行为兼容是两回事；V2 的 Plugin API、SDK、MCP 生命周期、Subagent 后台执行及 Windows Process Daemon 与 V1 有差异，不能因为 Session 保留就断言旧插件运行正确。

场景 A — Windows 11、PowerShell 5.1/7、OpenCode Desktop V1： Medium–High／迁移利好 + 兼容风险；行动 Test before upgrading；Breaking-risk Medium。 备份会话与配置，在测试 Windows 环境验证升级；检查项目目录、Session、Shell、Process Daemon、代理和退出码。安装成功不能代替端到端验收。

场景 B — V1 Plugins、Extensions、Skills、MCP： High／Breaking 风险；行动 Test before upgrading / Change plugins；Breaking-risk High（插件未适配时）。 逐项核对 Plugin API、事件与 Hooks、Tool Schema、SDK Imports、MCP Auth、Markdown Agent/Rules/Skills 发现路径。插件“能安装”不意味着权限和 Tool API 正确。

场景 C — 留在 V1 的生产环境： Low／中性；行动 No action；Breaking-risk Low。 入口是可选迁移，选择 Later 即可，不必为了提示立即升级。

谁可以忽略： 已在 OpenCode V2、不再使用 V1 的用户。

2.2 图片历史 25 MiB 裁剪与请求体过大自动 Compaction

变化内容： V1 历史图片数据超过 25 MiB 时，最旧的图片改为占位内容，避免向 Provider 发送超大请求；Provider 报 Request Body Too Large 时触发 Context Compaction 并重试，而非直接终止该 Turn。

技术意义： Context Token 上限与 HTTP Body Size 不相同。此机制可减少请求失败，但旧图片将不再完整参与后续推理，不能声称多模态长会话拥有完整历史记忆。

场景 A — 前端截图调试、视觉 Agent、多图片会话： Medium–High／稳定性利好 + 上下文损失风险；行动 Test before upgrading；Breaking-risk Medium。 用多张测试图片验证占位时机；关键截图须保留原始文件，需要时重新附加或显式读取。

场景 B — 第三方 API Gateway、Nginx、上传 Body 限制： Medium／兼容利好；行动 Test before upgrading；Breaking-risk Low–Medium。 核对 HTTP 413/Provider 特定错误、Compaction 重试次数和真实请求大小；该机制并不替代网关 Body Size/Timeout 设置。

谁可以忽略： 纯文本会话、不使用大量图片或不接近请求体限制者。

三、OpenCode PTY 0.6.0：Protocol 9 独立组件升级

发布时间： 2026-11-16 23:36 UTC / 北京时间 2026-11-17 07:36。

官方：process-daemon-v0.6.0 Release。

变化内容： packages/process-daemon 正式发行 @opencode/pty@0.6.0，Protocol 9，此前 0.5.x 使用 Protocol 8。Release 摘要没有公布完整 Wire Protocol 字段变化或 Client/Daemon 兼容矩阵。

技术意义： PTY 组件管理终端输入输出、进程启动、终端尺寸、退出状态和生命周期。Protocol 数字变化意味着集成方需要核对握手与版本协商，但不能仅凭 9 推断所有 8 客户端必然失效。此发行也不等于 OpenCode V1/V2 主程序同步升级。

场景 A — SDK/自研 Terminal Agent/直接依赖 @opencode/pty： Medium–High／潜在协议兼容风险；行动 Test before upgrading；Breaking-risk Medium–High（差异待验证）。 测试版本握手、错配、Resize、Ctrl+C、Timeout、断线重连、Session 恢复和资源清理。锁定成对 Client/Daemon 版本后再更新生产依赖。

场景 B — Windows PowerShell 5.1/7、后台 Shell、Runner： Medium／兼容风险；行动 Test before upgrading；Breaking-risk Medium。 以无副作用命令验证 UTF-8/GBK 输出、Exit Code、进程树、工作目录和取消信号。

场景 C — 普通官方 OpenCode V1/V2 用户： Low／中性；行动 No action；新增 Breaking-risk 未确认。 不必为独立 PTY 发布强制升级 CLI。

谁可以忽略： 无直接 PTY SDK、Process Daemon 协议或自定义终端扩展的用户。

六、Gemini CLI 与 Node.js 26：补报超时兼容风险

问题首次提交： 2026-11-13，涉及 Gemini CLI 0.68.0、Node.js 26.13.0；不是今日发布的正式修复。

官方仓库公开问题：gemini-cli #30280。

变化内容/证据性质： 这是仍开放、具备复现的 Issue。报告称 Node 26 内建 Fetch/Undici 所用 Global Dispatcher 标识与 Gemini CLI 捆绑的 Undici 不一致，造成部分模型请求没有应用 CLI 配置的响应头超时；预期约 60 秒，但测试中可能等到 Node 默认约 300 秒。报告使用本地 Mock Server，没有发起真实付费 API 请求。

技术意义： Node 升级能改变 HTTP Client、Proxy、Timeout 的实际运行语义，而非仅改变 JS 语法支持。Agent 的超时失效可能导致 CI 任务挂起、长时间重试及资源占用。

场景 A — Windows 11 + Gemini CLI 0.68.0 + Node 26： Medium–High／兼容风险；行动 Avoid untested Node 26 migration；Breaking-risk Medium。 若目前使用 Node 24 且稳定，先不要为追新版直接将生产 CLI 切到 Node 26；测试超时、代理、Ctrl+C、Exit Code。

场景 B — CI/Headless、第三方 Gemini API Gateway： High（依赖严格超时者）／可靠性风险；行动 Test before upgrading / Change runtime if affected；Breaking-risk Medium–High。 在本地模拟延迟响应头，验证失败时间、重试与 Runner Job Timeout；外层 Timeout 不能替代 HTTP 底层修复。

场景 C — Node 22/24 等其他组合： Low／未确认受影响；行动 No action；Breaking-risk 未确认。 报告的 Node 24.22.3 对照实验没有出现同一问题，但不能据此概括所有 Node 24 配置。

谁可以忽略： 未在 Node 26 下运行 Gemini CLI、且不依赖该请求超时路径者。问题尚待官方确认和正式修复；不能把 0.69 Preview 的其它变更当作已解决。
