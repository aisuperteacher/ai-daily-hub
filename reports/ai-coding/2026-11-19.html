二、OpenCode V2 2.3.1 / 2.3.2：优先处理执行语义变化

两版均在 2026 年 11 月 18 日正式发布；2.3.2 是当前核验的较新稳定版。

官方来源：OpenCode Changelog · 2.3.1 Release · 2.3.2 Release。

2.1 Shell 命令超时后默认转入后台，不再直接杀死

变化内容： 在 OpenCode 2.3.1 中，Shell Command 达到超时时间但仍在运行时，默认转入后台继续执行，任务结束后再报告结果。旧实验性 shell_timeout_background 开关不再决定是否启用，遗留配置仍能加载。前台命令设置 timeout: 0 现在表示采用默认 120 秒，不再表示无限等待。

技术意义： 这是 Timeout Semantics 的 Breaking Change。原来超时后进程被终止；现在可能是前台等待结束，但实际进程仍在编译、测试甚至写入文件。Shell Tool 返回与操作系统进程完成不再天然同步。

场景 A — Windows PowerShell 5.1/7、长时间 Maven/npm 构建。 严重度：High／可靠性利好 + 执行风险。行动：Test before upgrading。Breaking-risk：High。

例如 Maven 构建运行 180 秒，但前台等待设为 120 秒。新版可能在 120 秒时把构建放到后台，而不是取消它。如果此时 Agent 又启动第二次构建、删除 target 目录或进入下一步部署，两个操作可能相互干扰。

需要验证后台进程 ID、完成事件、退出码、进程清理以及同一目录的并发写入，不能仅凭 Shell Tool 的第一条回复判断任务已经成功。

场景 B — CI/Headless、自动化部署、数据库迁移脚本。 严重度：High／Breaking 风险。行动：Change orchestration / Test before upgrading。Breaking-risk：High。

原本依赖 Tool Timeout 来终止子进程的控制流程必须重新审查。应增加真正的业务级终止机制、任务状态跟踪和超时后的取消/补偿逻辑；不要让后台部署与后续操作无序并发。

谁可以忽略： 只运行很短的 Shell 命令、不依赖 Timeout 控制进程生命周期的用户。

2.2 Background Compaction 默认开启

变化内容： 当 Session 接近自动上下文压缩阈值，OpenCode 会提前在后台生成摘要，降低用户下一轮消息等待 Compaction 的概率。

如果要关闭：

{
  "compaction": {
    "background": false
  }
}

旧的 experimental.background_compaction 配置已经被新的正式配置路径取代。

技术意义： Compaction 从按需阻塞操作变为预测性后台任务。速度可能提升，但即使最后没有使用预生成摘要，也可能产生 Token 消耗。

场景 A — 长 Context、多 Agent、长代码审查任务。 严重度：Medium–High／体验利好 + 成本风险。行动：Test before upgrading。Breaking-risk：Medium。

在相同模型和 Prompt 下记录 Compaction 次数、后台摘要请求、实际总费用和摘要是否保持关键任务状态。尤其多 Agent 场景中，不要误以为所有后台摘要都一定被后续 Session 使用。

场景 B — 低频会话、严格费用预算的 API Key 用户。 严重度：Medium／成本风险。行动：Change config（必要时）。Breaking-risk：Low–Medium。

如果提前生成摘要的成本高于节约的等待时间，可以关闭 Background Compaction。

谁可以忽略： 短会话、不接近上下文阈值或完全不关心后台摘要开销的用户。

2.3 Schedules 迁移为 Automations：条件任务可能被丢弃

变化内容： 2.3.1 将实验性 Schedules 演进为 Automations，由 automations Feature Flag 控制，旧 schedules Flag 暂时兼容。

Automations 可以按指定时间、间隔、Cron 或推送的 MCP Event 运行，发送 Prompt 给指定 Session / Subagent，或由 Code Mode Program 决定是否继续执行。

迁移时，原先仍处于启用或暂停状态的普通 Prompt Schedules 会保留；带有 Condition、Run Limit 的旧 Schedules，以及已经完成的 Schedules，不会完整迁移。 官方新增 /automation 及 automation_* 工具入口。

技术意义： 这是任务数据模型的迁移，不是简单改名。旧任务在配置中存在过，不代表升级后一定仍在 Automation Registry 里。

场景 A — OpenCode 定时 Agent、自动日报、CI 触发工作流。 严重度：High／新能力利好 + 任务丢失风险。行动：Test before upgrading / Change config。Breaking-risk：High（使用条件调度或运行次数限制时）。

升级前导出当前任务定义及状态，升级后逐项核对任务数量、条件、目标 Session、实际触发时间和 MCP Event。对被迁移逻辑丢弃的任务，应基于原定义人工重建，不要让重复任务与旧调度同时执行。

场景 B — 自建 Agent Harness、MCP 事件驱动自动化。 严重度：Medium–High／编排利好。行动：Test before adopting。Breaking-risk：Medium。

MCP Event 可能重复或迟到，需增加事件 ID、去重和权限控制。Code Mode 决定是否运行的逻辑不能代替服务端业务授权。

谁可以忽略： 从未使用 OpenCode 实验性 Schedules / Automations 的用户。

2.4 CLAUDE.md 与 AGENTS.md 发现规则调整

变化内容： 2.3.1 恢复了读取 CLAUDE.md 的部分兼容逻辑：目录中没有 AGENTS.md 时可读取该目录的 CLAUDE.md；缺少全局 AGENTS.md 时，可回退到 ~/.claude/CLAUDE.md。

设置 OPENCODE_DISABLE_CLAUDE_CODE 或 OPENCODE_DISABLE_CLAUDE_CODE_PROMPT，可以跳过相关 CLAUDE.md 指令加载。

技术意义： 指令发现改变会影响 Agent 的 System/Developer Prompt 拼装。代码仓库没有变化，但 Agent 的行为可能因额外加载旧 CLAUDE.md 而发生变化。

场景 A — 同时使用 Claude Code、Codex、OpenCode 的仓库。 严重度：High（存在不同规则时）／兼容利好 + 指令冲突风险。行动：Test before upgrading / Change config。Breaking-risk：Medium–High。

检查根目录、子目录、全局规则内容是否有相互矛盾的要求，避免旧规则重新加载后覆盖团队期望的工作流程。不要把文件名相似理解为跨产品有完全一致的权限优先级。

场景 B — OpenCode 独立项目，无 CLAUDE.md。 严重度：Low／中性。行动：No action。Breaking-risk：Low。

谁可以忽略： 没有兼容 Claude Rules 需求、且未存放 CLAUDE.md 的用户。

2.5 Code Mode 结构化 read 返回值、Plugin Tool Rename

变化内容： 2.3.1 调整 Code Mode 与 Plugins 接收到的 read Tool Result，区分文本（含 offset、lineCount、next）、目录条目和媒体 URI 等结构化结果，而不是让插件依赖旧的混合表示。

另外，Plugin 的 tool.execute.before 重命名 Tool 的行为现在可以应用到 Code Mode 内部 Tool Calls；调用不存在的 Tool 会返回被拒绝的 Promise，允许 .catch()、Promise.allSettled() 按预期处理。Code Mode 还可使用 Node.js Buffer，并支持更简洁的 Search 调用形式。

技术意义： Tool 的模型可见摘要与扩展代码接收的数据结构不同。此次变化主要影响直接调用底层 Tool API 的扩展作者，而不是所有模型回答。

场景 A — TypeScript SDK、Code Mode Extensions、Plugin Hooks。 严重度：High（直接集成者）／API 兼容利好 + Breaking 风险。行动：Change code / Test before upgrading。Breaking-risk：High。

检查旧代码是否直接读取 read 的字符串或旧属性，分别测试文件、目录、媒体、空结果以及不存在的 Tool。对 Tool Rename，应核验重命名后实际工具身份和权限仍然正确。

场景 B — 仅使用官方 TUI 内置工具。 严重度：Low／中性。行动：No action。Breaking-risk：Low。

谁可以忽略： 不编写 OpenCode SDK 或 Code Mode 扩展的用户。

2.6 GPT-6.2 Prompt Caching 修复：多轮成本可能显著下降

变化内容： OpenCode 2.3.2 修复 GPT-6.2 使用 Responses API 时的 System Prompt 缓存失效问题。

原先通过 Responses instructions 字段发送的 System Prompt 可能在每一步被当作未缓存输入重新计费；现在在 OpenAI、ChatGPT Sign-in、GitHub Copilot、Zen、Azure、OpenRouter 等 Responses 路径上，将该 Prompt 作为前置 Developer Message 发送，使后续步骤可以复用缓存前缀。

官方给出的例子中，GitHub Copilot gpt-6.2-sol 每步未缓存输入从约 14,000 Tokens 降到 3 Tokens，这是具体测试场景，不代表所有 Provider 都有相同降幅。/responses/compact 也会读取相同的缓存前缀。

技术意义： Prompt Caching 是否命中，不只取决于 Model ID，也取决于消息字段、角色、顺序和 Provider 是否支持对应缓存语义。

场景 A — GPT-6.2、OpenAI-compatible Gateway、OpenRouter、Azure。 严重度：Medium–High／成本与性能利好 + 兼容风险。行动：Test before upgrading。Breaking-risk：Medium。

核对真实请求是否采用新的 Developer Message 格式，Gateway 是否接受该结构，缓存读写统计是否准确。不要将官方示例的 Token 减少幅度直接套用到自己的账单。

场景 B — 长会话、多次 Tool Calling、频繁 Compaction。 严重度：Medium–High／成本利好。行动：Upgrade after canary。Breaking-risk：Low–Medium。

建议对比两版相同任务的 input_tokens、cached_tokens、输出 Tokens 及总费用。

谁可以忽略： 不使用 GPT-6.2 或相关 Responses 路径的用户。

2.7 Windows WinGet 安装渠道落后于正式发行

变化内容： OpenCode 仓库在 2026 年 11 月 18 日收到并确认了一个 Windows 安装渠道问题：当时 Anomaly.OpenCode 的 WinGet CLI Manifest 仍为 2.2.7，Desktop Manifest 为 2.3.0，而 GitHub 正式发行已达 2.3.2。

从 WinGet 安装的 OpenCode，执行 opencode upgrade 时可能依赖 WinGet 所报告的最新版本，因此会提示已是最新，而实际上并未升级。该问题有官方仓库 Issue 的复现与维护者回应，但尚不能宣称所有 Windows 用户或未来的 WinGet 状态都如此。

场景 A — Windows 11 + PowerShell + WinGet 安装。 严重度：High（需要新版本修复者）／升级渠道风险。行动：Change install strategy / Test before upgrading。Breaking-risk：Medium。

winget list --id Anomaly.OpenCode -e
winget show --id Anomaly.OpenCode -e
opencode --version

如果 WinGet 的可用版本明显滞后，优先核对官方 GitHub 发布包与安装指南；迁移安装方式前备份配置和 Session，避免不同安装渠道的可执行文件互相覆盖。

场景 B — npm/global、官方独立安装器。 严重度：Low–Medium／中性。行动：No action / Verify actual version。Breaking-risk：Low。

谁可以忽略： 不通过 WinGet 安装 OpenCode 的用户。

三、Codex CLI 0.170.0：权限、MCP 与 Windows 可靠性

正式发布：2026-11-18 03:40 UTC，即北京时间 2026-11-18 11:40。

官方来源：Codex 0.170.0 GitHub Release · OpenAI Codex 官方 Changelog。

3.1 MCP OAuth 登录、取消、注销的并发竞争修复

变化内容： 0.170.0 修复 MCP OAuth 凭据在用户取消操作、Login 和 Logout 并发发生时的竞争问题。

技术意义： OAuth 凭据刷新与生命周期操作存在顺序依赖。旧请求的完成结果不能覆盖较新的登录或注销状态，否则可能发生“用户以为已注销，但旧认证信息仍被使用”或突然掉线。

场景 A — Remote MCP、多个身份、企业 OAuth Connector。 严重度：High／认证安全与正确性利好。行动：Test before upgrading。Breaking-risk：Medium。

验证登录后取消、刷新过程中注销、多个 Session 同时访问同一 Server，以及重新登录后的实际身份。测试时只记录身份状态，不输出 Refresh Token。

场景 B — 本地 Stdio MCP、无 OAuth。 严重度：Low／中性。行动：No action。Breaking-risk：Low。

谁可以忽略： 不使用 MCP OAuth 的 Codex 用户。

3.2 Sandbox 权限更新和子线程不再丢失既有约束

变化内容： 0.170.0 修复了 Permission Update 和 Child Threads 某些情况下没有保留原有 Sandbox Restrictions 的问题。Windows 文件替换时的权限保留也获得修复。

技术意义： 当 Agent 创建 Child Thread 或调整部分权限时，原先仍然有效的限制不应被意外丢失。对多 Agent 和无人值守执行系统，这比普通 UI 修复重要得多。

场景 A — Windows Sandbox、codex exec、多 Agent。 严重度：High／安全利好 + 兼容风险。行动：Upgrade after canary。Breaking-risk：Medium–High。

使用无副作用的权限测试，验证子线程不能写入原本被限制的路径、不能访问未授权网络，且 Permission Profile 切换不会清除既有 Deny。

场景 B — 企业 CI / Headless Runner。 严重度：High／治理可靠性利好。行动：Test before upgrading。Breaking-risk：Medium–High。

升级后原本错误获得权限的任务可能开始失败，这属于需要修复的执行策略问题，而不是应当直接取消 Sandbox 的理由。

谁可以忽略： 没有多线程/动态 Permission Update、只在普通默认受信任 Session 中工作的人可忽略专项回归。

3.3 Windows 文件替换、Runtime Registration 与网络回退

变化内容： 0.170.0 修复 Windows 文件替换时的行为和 Sandbox Permission Preservation、Runtime Registration 恢复问题。

同时，WebSocket 请求体过大时，会更直接地回退到 HTTP，而不是进行不必要的重试。Cloud Conversations 的自动重连更稳定，客户端重连时保留仍在进行的 Recovery Turns。

技术意义： Runtime、Transport 和 Session Recovery 是不同故障层。WebSocket 回退不等于所有第三方 Gateway 必然兼容 HTTP 路径；Cloud 重连成功也不等于业务写操作绝对没有重复。

场景 A — Windows 11、PowerShell 5.1/7、临时文件替换。 严重度：Medium–High／可靠性利好。行动：Test before upgrading。Breaking-risk：Medium。

测试文件写入、重命名、覆盖、锁定文件、Sandbox 目录权限及恢复后的文件内容。

场景 B — 第三方 Gateway、WebSocket、长会话、远程 Agent。 严重度：Medium–High／网络兼容利好。行动：Test before upgrading。Breaking-risk：Medium。

验证 WebSocket 大请求、HTTP Fallback、TLS、代理、Cloud Session 恢复及副作用幂等性。

谁可以忽略： 不使用 WebSocket/Cloud Connection、也不受 Windows 文件替换问题影响的用户。

3.4 TUI WebRTC Voice、同名 MCP Server、OTel Header 自动刷新

变化内容： Codex 0.170.0 增加 TUI 实时语音通话的 WebRTC 协商能力；新增实验性支持不同 Environment 中存在同名 MCP Server；OpenTelemetry HTTP Exporter 可以自动刷新认证 Header。

技术意义： 语音涉及新的实时连接与授权；MCP Server 同名则涉及 Server Namespace，不能只依赖短名称来确认真正调用目标；Telemetry Token 自动刷新可以减少长期 Agent 的监控中断，但不意味着凭据权限可以无限扩大。

场景 A — TUI 语音、Windows 终端。 严重度：Medium／新能力利好。行动：Test before adopting。Breaking-risk：Low–Medium。

验证实际客户端是否支持语音入口、麦克风权限和网络 WebRTC 连接。发行说明只确认协商能力，不保证所有账户、地区和终端均已开放完整语音界面。

场景 B — 多 Environment、Remote MCP、相同 Server Name。 严重度：Medium–High／实验能力利好 + 命名冲突风险。行动：Test before enabling。Breaking-risk：Medium。

验证不同 Environment 的 Server Identity、Tool Discovery、OAuth 身份与执行权限，不要让同名服务误路由。

场景 C — OTel Collector、企业监控、长期 Runner。 严重度：Medium／可观测性利好。行动：Test before upgrading。Breaking-risk：Low–Medium。

测试 Exporter 凭据过期、刷新失败、重试和日志脱敏，不能把认证 Header 打印进公开日报或 CI 日志。

谁可以忽略： 不使用 TUI 语音、实验性多环境 MCP 或 OTel HTTP Exporter 的用户。

四、Claude Code 2.1.327：优先关注文件保护、MCP 与配置完整性

发布于 2026-11-17 23:17 UTC 左右，即北京时间 2026-11-18 07:17。

官方来源：Claude Code 2.1.327 Release。发行内容另经同步的 完整变更记录 核对。

4.1 Remote Control / Worktree 停止时误删 Git-Ignored 文件的修复

变化内容： 2.1.327 修复了 Remote Control 在 Worktree 模式停止服务时，可能删除仍在运行 Session 的 Git-Ignored 文件，例如 .env 的问题。

此外，修复 Self-hosted Runner 开启 --use-anthropic-git-proxy 时，因 GIT_CONFIG_GLOBAL 指向一个已有非空目录而错误删除该目录的情况。新版会保留目录、忽略该变量并发出警告。

技术意义： Agent 的 Session Cleanup 和进程终止不能越过文件所有权边界。.env 虽然被 Git 忽略，但可能包含本地运行配置，不能被当作安全可删除的临时文件。

场景 A — Windows Git Worktree、远程 Agent、Claude Remote Control。 严重度：High／数据保护利好。行动：Upgrade now after canary。Breaking-risk：Medium。

准备可销毁的测试仓库和无敏感内容的 .env，验证停止 Remote Control、Session 重连与 Worktree 清理，不应删除仍由会话使用的文件。

场景 B — Self-hosted Runner、SSH、Git Proxy。 严重度：High／文件安全利好 + 环境行为变化。行动：Test before upgrading。Breaking-risk：Medium。

检查 GIT_CONFIG_GLOBAL 的真实类型与路径，确认服务不会删除现有目录，并正确处理警告。不要在生产服务器上通过故意破坏真实 Git 配置来测试。

谁可以忽略： 不使用 Remote Control、Worktree 或 Self-hosted Git Proxy 的个人交互用户。

4.2 claude mcp add-json 支持标准输入，降低命令行凭据暴露

变化内容： 2.1.327 新增 claude mcp add-json <name> -，从 stdin 读取 MCP Server 的 JSON 配置，而不是必须把 JSON 原文作为命令行参数传递。

它需要在 Claude Code Session 外的系统终端执行，不能直接在 Claude Code 交互 Session 内使用。

技术意义： 命令行参数可能被 Shell 历史、进程检查器、终端日志或自动化平台捕获。通过标准输入传递配置可减少这一暴露面，但不代表凭据存储文件本身已被加密。

场景 A — Windows PowerShell、Remote MCP、OAuth/API Key。 严重度：Medium–High／凭据安全利好。行动：Test before adopting。Breaking-risk：Low。

例如从一个已妥善保护、采用 UTF-8 编码的测试配置文件读取：

# 仅使用不含真实密钥的测试配置
Get-Content -LiteralPath .\mcp-test.json -Raw |
  claude mcp add-json demo-server -

检查配置是否写入预期 Scope、是否保留 JSON 结构。不要在历史命令中粘贴真实 Token。

谁可以忽略： 不使用 claude mcp add-json 或不需要从命令行安装 MCP Server 的用户。

4.3 Project MCP 增删不再破坏 .mcp.json 的其它字段

变化内容： 修复 claude mcp add / claude mcp remove 在 Project Scope 操作时，可能删除 .mcp.json 中其它顶层键，例如 $schema 或其它工具自定义的 servers 配置。

技术意义： 配置更新应当是目标字段的定向修改，而不是把自己无法识别的字段全部丢弃。对多个 Agent 共享一个配置仓库的团队，这属于重要的数据完整性修复。

场景 A — 多 MCP Server、共享仓库、跨工具配置。 严重度：High／配置完整性利好。行动：Upgrade after canary。Breaking-risk：Low–Medium。

备份测试 .mcp.json，分别执行添加与删除测试 Server，验证未知顶层键和其它 Server 配置仍被保留。

谁可以忽略： 没有项目级 .mcp.json 或不使用 Claude 命令管理 MCP 的用户。

4.4 /status 增强 Skills、Hooks、权限配置故障诊断

变化内容： /status 可以显示加载失败的 Agent、Skill、Command、Output Style，Keybinding 错误、不可用 Sandbox、被忽略的 Permission Settings，以及永远不会匹配的 Hook Matchers。

/config 也会提示某一配置项是否被其它更高优先级设置覆盖。Gateway Hint Headers 新增可选的 x-claude-code-managed-settings-checksum；需要配置 CLAUDE_CODE_GATEWAY_HINT_HEADERS=1 的托管启用条件。

技术意义： “配置文件存在”与“实际已加载生效”是两件事。特别是 Permission Deny、PreToolUse Hooks 和 Skills Discovery，静默失效往往比启动失败更危险。

场景 A — Windows + PowerShell Hooks、Skills/Plugins、Managed Settings。 严重度：High（依赖安全 Hook 者）／可观测性利好。行动：Test before upgrading。Breaking-risk：Low–Medium。

升级后使用 /status 和 /config 检查文件是否被实际加载、Hook Matcher 是否能匹配真实 Tool，以及企业托管权限是否覆盖本地配置。

场景 B — 第三方 Gateway、企业多机配置一致性。 严重度：Medium／治理利好。行动：Test before adopting。Breaking-risk：Low。

Managed Settings Checksum 可用于诊断配置漂移，但不能把它当作数字签名或独立安全认证机制。

谁可以忽略： 没有自定义 Hooks、Skills、权限规则和企业托管配置的用户。

4.5 GitHub 安装、导出覆盖与停止命令竞态修复

变化内容： /install-github-app 修改仓库前现在要求确认；/export 在覆盖已有文件前要求确认。

另修复 Cloud 或 Self-hosted Runner 某些无 Feature Flags 场景中，用户按 Stop 后，迟到的审批结果可能让已批准的命令继续执行的问题。

技术意义： 这些改动涉及不可逆副作用的确认时机。安装 GitHub App、覆盖文件以及停止正在执行的命令，不应该只凭过期的授权结果继续操作。

场景 A — GitHub 仓库管理、导出脚本、文件覆盖。 严重度：Medium–High／数据保护利好。行动：Test before upgrading。Breaking-risk：Medium。

检查覆盖确认、拒绝后的文件完整性、无界面模式下的失败状态，避免自动化卡在无人处理的确认界面。

场景 B — Cloud Runner、远程 Agent、权限审批。 严重度：High／安全利好。行动：Upgrade after canary。Breaking-risk：Medium。

验证 Stop 后原命令不会因延迟审批再次继续执行。

谁可以忽略： 不使用上述 GitHub、Export、Remote Runner 功能的用户。
